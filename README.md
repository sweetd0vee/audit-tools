# Audit Tools

Локальная система сопровождения внутренней аудиторской проверки банка в Республике Беларусь.

Аудитор описывает проверку. Система собирает нормативную базу (НПА), даёт читать саммари вместо кодексов целиком, отвечает на вопросы по документам с цитатами и дальше ведёт рабочие документы проверки. Клиентские данные и формулировки проверки **не уходят в интернет**: поиск только по официальным доменам РБ, модели крутятся локально.

Это не «ещё один чат с LLM». Чат — поверхность. Ядро продукта — **Audit Tool Server**: кейс проверки, библиотека НПА, тесты, рабочие бумаги (WP), правила.

**Как работать аудитору** — гайд с навигацией Open WebUI, историями и объяснением, что видит модель: [`docs/GUIDE.md`](docs/GUIDE.md). Краткая шпаргалка команд: [`docs/AUDITOR.md`](docs/AUDITOR.md).

Коробка: [`docs/VISION.md`](docs/VISION.md) · [с чего писать](docs/START.md) · [архитектура](docs/ARCHITECTURE.md) · [план](docs/PLAN.md) · [идеи](docs/IDEAS.md).

## Зачем это нужно

Внутренний аудитор банка каждый раз заново:

1. вспоминает, какие законы, инструкции НБРБ, НК/ГК и внутренние политики относятся к теме;
2. ищет актуальные редакции на pravo.by / nbrb.by;
3. читает десятки страниц, чтобы вытащить 5–7 релевантных норм;
4. проектирует тесты, собирает выборку, пишет working papers.

Модель без документов галлюцинирует статьи. Документы без модели не масштабируются. **RAG + доменный сервер** закрывают разрыв: модель думает, НПА доказывают, аудитор подтверждает.

Инвариант продукта:

> Модель не заменяет чтение первоисточника и не ставит аудиторское суждение. Она ускоряет поиск нормы, черновик теста и черновик WP. Цитата проверяется по файлу в кейсе.

## Что собираем, что пишем сами

Стек — сборка готовых локальных сервисов вокруг **одного custom-бэкенда**. Мы не форкаем Open WebUI и не пишем свою LLM.

| Компонент | Роль в продукте | Свой код? |
|---|---|---|
| **Open WebUI** | UI аудитора: чат, Knowledge, RAG, Functions | Нет — ставите |
| **Open WebUI Function Pipe** | Agent loop: фазы проверки, HITL, вызов backend API | Да — один paste-файл Pipe |
| **Ollama** | Локальные LLM и embeddings | Нет — ставите |
| **SearXNG** | Веб-поиск только по allowlist (`pravo.by`, `nbrb.by`, …) | Нет — ставите |
| **Серверный индекс + Open WebUI Knowledge** | Поиск по НПА кейса; Knowledge sync опционален | Частично — индекс в backend |
| **Audit Tool Server** | FastAPI: кейсы, данные, тесты, WP, rules | **Да — главный custom** |
| **Continue.dev / Aider** | IDE-режим как Cursor (позже) | Нет — ставите |

### Как это стыкуется

```
Аудитор
  ├─ Open WebUI ───────── чат и Function Pipe «Аудитор»
  │     └─ Pipe ───────── фазы проверки, HITL, вызов API
  └─ Audit Tool Server ── FastAPI (этот репозиторий)
        ├─ кейс проверки, библиотека НПА
        ├─ ingest / индекс / ask / саммари / total / программа / гипотезы
        ├─ Ollama (на хосте): генерация + embeddings
        ├─ SearXNG: добыча актов, не чат
        └─ позже: данные клиента, тесты, WP, rules
```

**Open WebUI** — витрина: «спросить закон», прикрепить коллекцию Knowledge, запустить функцию/пайплайн.

**Audit Tool Server** — система записи: что проверяем, какие акты утверждены аудитором, какие файлы скачаны, какие чанки проиндексированы, какие тесты и WP появятся дальше. Без него чат не знает контур проверки и не умеет отличить ГК от выписки клиента.

**Function Pipe «Аудитор»** — клей агента: не дублирует бизнес-логику сервера, а вызывает его API по фазам («собери библиотеку» → «задай `вопрос …`» → «саммари / total / программа»). Pipelines остаются запасной идеей, не текущий primary path.

**SearXNG** — только добыча официальных текстов в библиотеку кейса. Не основной RAG в каждом вопросе.

**Continue.dev / Aider** — отдельный контур «поправить правило / шаблон WP в IDE». В v1 не нужен.

## Продуктовый контур проверки

Один **кейс** = одна проверка (название, ключевые слова, период).

```
1. Библиотека НПА      ← сейчас (чат: описать → утвердить → скачать)
2. База знаний / RAG   ← сейчас (команда «вопрос …» с цитатами)
3. Саммари Word        ← сейчас («саммари» — из скачанных актов)
4. Total саммари       ← сейчас («саммари total» — из знаний модели, не из базы)
5. Программа Word      ← сейчас («программа проверки»)
6. Гипотезы Excel      ← сейчас («гипотезы» — чеклист для проверки)
7. Обычный чат         ← сейчас (без префикса «вопрос» — диалог, не цитата)
8. Данные клиента      ← план
9. Тесты и выборка     ← план
10. Working papers     ← план
11. Правила (rules)    ← план
```

Агентные фазы 1–7 закрывает Pipe «Аудитор». Данные / тесты / WP — план.

### 1. Библиотека НПА (готово)

Аудитор вводит название проверки и keywords. Локальная LLM предлагает список актов (закон / кодекс / инструкция / постановление) с приоритетом и обоснованием. Аудитор **валидирует** список — без этого шага ничего не скачивается.

Добыча файла:

1. ручной URL, если аудитор его знает;
2. curated `known_sources` (официальные ссылки на известные акты);
3. SearXNG строго по allowlist доменов РБ.

Клиентские данные в поиск не отправляются.

Allowlist:

- `pravo.gov.by` / `pravo.by` / `etalonline.by`
- `nbrb.by`
- `minfin.gov.by`
- `nalog.gov.by`
- `government.by`
- `president.gov.by`

Результат: папка кейса + zip-архив библиотеки.

### 2. База знаний и RAG (готово)

Скачанные HTML/PDF чистятся в текст, режутся на чанки (в т.ч. по статьям), считаются embeddings через Ollama, пишутся саммари «для аудитора, который не будет читать весь акт».

В продуктовом чате два разных режима (их нельзя путать):

| Режим | Как вызвать | Откуда ответ |
|---|---|---|
| Норма с цитатой | начать сообщение со слова `вопрос` | `POST …/knowledge/ask`, только чанки скачанной библиотеки |
| Обычный диалог | писать без префикса | `POST /api/v1/chat`, знания модели, **не** цитата из кейса |

Коллекция Open WebUI Knowledge — опциональный дубль `.txt`, если задан API-ключ. В KB нормативки **не кладём** Excel/выписки клиента — иначе модель смешает «что требует закон» и «что в файле клиента».

Подробная модель RAG: [`docs/RAG_для_разработчика.md`](docs/RAG_для_разработчика.md).

### 3. Саммари Word (готово)

Когда библиотека скачана, аудитор пишет в чате `саммари`. Сервер по каждому акту пишет карточку существенного для этой проверки (короткий акт — one-shot, длинный — query-focused RAG по keywords, не map-reduce по всему кодексу), синтезирует обзор и отдаёт `.docx` со ссылками `[n]`. Полный текст в чат не выкладывается. Пересборка: `саммари заново`.

Как пользоваться: [`docs/GUIDE.md`](docs/GUIDE.md). Как устроен конвейер и большая библиотека: [`docs/SAMMARI.md`](docs/SAMMARI.md).

### 4. Программа проверки Word (готово)

Аудитор пишет `программа проверки`. Сервер собирает черновик программы аудиторской проверки банка РБ по названию проверки, keywords и приложенным актам и отдаёт `.docx`. Это не утверждённая программа СВА и не суждение. Пересборка: `программа проверки заново`.

### 5. Total саммари Word (готово)

Аудитор пишет `саммари total` (синонимы: `конспект модели`). Один вызов LLM **без** опоры на скачанные файлы: конспект по теме проверки из знаний модели, со ссылками на акты, которые модель помнит. Это не цитата из кейса. Сверять с первоисточником / с `саммари`. Пересборка: `саммари total заново`.

### 6. Гипотезы Excel (готово)

Аудитор пишет `гипотезы`. Сервер собирает чеклист 8–10 гипотез проверки в `.xlsx` (и markdown-копию). Опирается на уже собранные саммари / total / программу и фрагменты НПА, если они есть. Это черновик планирования, не суждение. Пересборка: `гипотезы заново`.

### 7. Обычный чат (готово)

Без префикса `вопрос` Pipe вызывает `POST /api/v1/chat`: план, формулировки, риски — из знаний модели, без блока цитат. Это не норма из библиотеки.

### 8–11. Данные, тесты, WP, rules (план)

Это и есть причина, почему custom-сервер главный, а не обёртка над чатом.

- **Данные** — первичка проверки (выгрузки, договоры, обороты). Вопросы «сколько начислено» идут через код/tools, не через RAG по таблицам.
- **Тесты** — процедуры: что смотрим, на какой выборке, какой критерий «ок / находка». Модель предлагает черновик, аудитор утверждает.
- **Working papers** — слепок доказательства: норма → факт → вывод. Генерация черновика, не подпись.
- **Rules** — кодифицированные проверки (курсы, лимиты, признаки связанности), которые можно гонять детерминированно и вызывать из пайплайна.

### Агентные фазы (частично)

Сейчас Pipe «Аудитор» закрывает библиотеку, саммари, саммари total, программу проверки, `гипотезы`, HITL по гипотезам, `аудиторское мнение`, `аудиторское заключение`, `вопрос …` и обычный чат. Дальше — те же фазы в коде Pipe + API сервера для данных, тестов и WP, не универсальный ReAct.

## Принципы (не ломаем)

1. **Human-in-the-loop.** Список НПА и гипотезы для мнения утверждает аудитор.
2. **Локальность.** Ollama, Open WebUI, SearXNG, векторная БД — на своей машине/контуре.
3. **Allowlist поиска.** Никакого «погугли за меня» по всему интернету.
4. **Норма ≠ факт.** База НПА и данные клиента — разные коллекции и разные tools.
5. **Цитата важнее гладкого ответа.** Нет фрагмента — модель должна отказаться, а не сочинить статью.
6. **Audit trail.** Какой файл, какой чанк, какой URL попал в ответ — должно быть восстановимо из кейса.

## Локальный запуск

Продукт — **один URL**: [http://localhost:3000](http://localhost:3000) (Open WebUI).  
Swagger [http://localhost:8100/docs](http://localhost:8100/docs) — для разработки tools, не для аудитора.

Ollama на хосте (`http://localhost:11434`). На Windows включите «Expose Ollama to the network», иначе контейнеры не достучатся.

```powershell
cd c:\Users\audit\Work\Arina\2026\audit-tools
docker compose up -d --build
```

После `up`: http://localhost:3000 → новый чат → модель **Аудитор**. Что писать — [`docs/GUIDE.md`](docs/GUIDE.md). Настроить Open WebUI: [`docs/OPENWEBUI.md`](docs/OPENWEBUI.md). Поставить Pipe: [`seed/openwebui/AGENT.md`](seed/openwebui/AGENT.md), засев Admin — [`seed/openwebui/README.md`](seed/openwebui/README.md).

Модели (см. `backend/.env.example`):

- чат: `qwen3.8:27b` (или другая сильная локальная с большим `num_ctx`)
- embeddings: `qwen3-embedding:latest` — **не** MiniLM: юридический русский

Лабораторный React (не продукт):

```powershell
docker compose --profile lab up -d
```

http://localhost:5174 — только отладка API, пока tools в чате не готовы. `frontend/` не развиваем.

Без Docker backend можно поднять отдельно:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
uvicorn app.main:app --reload --host 127.0.0.1 --port 8100
```

Подробный API-flow библиотеки — в [`backend/README.md`](backend/README.md).

## Граница продукта

| Делаем | Не делаем |
|---|---|
| Собрать и обосновать библиотеку НПА по теме проверки | Юридически значимое заключение «за аудитора» |
| RAG с цитатами по утверждённым актам | Поиск по всему интернету и чужим юрисдикциям |
| Черновики тестов и WP (план) | Подмену выборки, пересчёта и суждения аудитора |
| Локальный контур банка | SaaS с отправкой клиентских файлов во внешние LLM |
| Свой доменный сервер + сборка стека | Форк Open WebUI / своя модель с нуля |
