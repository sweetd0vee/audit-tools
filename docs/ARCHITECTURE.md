# Архитектура: сборка, не форк

Цель архитектуры — **коробочный продукт** ([VISION.md](VISION.md)) при минимальном своём коде. Каждая строка, которую мы пишем, должна закрывать дыру, которой нет в Open WebUI / Ollama / SearXNG / DuckDB / шаблонах Word.

Если функцию можно включить настройкой или тонким tool-скриптом — своего сервиса нет.

---

## 1. Слой за слоем

```
┌─────────────────────────────────────────────────────────────┐
│  Поверхность (готовое)                                      │
│  Open WebUI — чат, Knowledge, citations, auth, Files        │
│  Опционально позже: Continue.dev в IDE для правил/шаблонов  │
└────────────────────────────┬────────────────────────────────┘
                             │ Functions / Pipelines / OpenAPI tools
┌────────────────────────────▼────────────────────────────────┐
│  Клей агента (почти готовое + тонкие скрипты)               │
│  Open WebUI Pipelines / Tools                               │
│  Фазы: библиотека → вопросы к НПА → данные → тесты → WP     │
└────────────────────────────┬────────────────────────────────┘
                             │ HTTP
┌────────────────────────────▼────────────────────────────────┐
│  Свой код (единственное ядро)                               │
│  Audit Tool Server — FastAPI                                │
│  кейс, HITL, добыча НПА, ingest, данные, тесты, WP, rules,  │
│  audit trail                                                │
└──────────────┬─────────────┬──────────────┬─────────────────┘
               │             │              │
        ┌──────▼──────┐ ┌────▼─────┐ ┌──────▼──────┐
        │ Ollama      │ │ SearXNG  │ │ DuckDB /    │
        │ LLM+embed   │ │ allowlist│ │ файлы кейса │
        └─────────────┘ └──────────┘ └─────────────┘
                             │
                    Open WebUI Chroma (индекс чата)
```

**Правило стыковки:** Pipelines не содержат бизнес-логики. Они вызывают API сервера и показывают аудитору результат. Сервер не рисует UI.

## 2. Что берём готовым, что пишем

| Компонент | Роль | Свой код | Статус |
|---|---|---|---|
| **Open WebUI** | Единственная поверхность аудитора | Нет — ставим и **засеваем** (модель, RAG-шаблон, tools, pipeline) | выбран |
| **Open WebUI Pipelines** | Фазы проверки, HITL в чате | Тонкий pipeline (~файл), не форк | план |
| **Open WebUI Functions/Tools** | Pipe «Аудитор» вызывает API; Tools — запасной native FC | Тонкие HTTP-обёртки + Pipe | есть (чат) |
| **Ollama** | LLM + embeddings | Нет | есть |
| **SearXNG** | Добыча актов, не RAG в каждом вопросе | Нет — свой `settings.yml` с allowlist | есть |
| **Chroma в Open WebUI** | Индекс Knowledge для чата | Нет | есть (sync) |
| **DuckDB** | SQL по выгрузкам клиента, без своей аналитической UI | Нет — tool «выполни SQL» | план |
| **python-docx / шаблоны банка** | Черновик WP в `.docx` | Шаблоны + заполнение полей | план |
| **Docker Compose (+ Caddy)** | Коробка: один URL, один `up` | compose, env, seed | план |
| **Audit Tool Server** | Система записи и домен РБ | **Да — главный custom** | есть (шаги 1–2) |
| **React `frontend/`** | Лаборатория API | Не продукт. Не развивать | прототип |

Continue.dev / Aider — отдельный контур «править rule / шаблон WP в IDE». В коробке v1 не нужен.

## 3. Решение по фронтенду

**Продуктовый UI свой не пишем**, пока не доказано, что чат не тянет HITL.

Поток «создать кейс → модель предложила список НПА → аудитор утвердил (номера или `плюс Название акта`) → скачать → саммари / вопросы» — это не экран, это **диалог с явным подтверждением**. Гайд для аудитора: [GUIDE.md](GUIDE.md). Шпаргалка команд: [AUDITOR.md](AUDITOR.md).

```
Аудитор: Проверка аренды коммерческой недвижимости,
         аренда, валюта, НДС

Агент:   [create + propose]
         Предлагаю 12 актов. Обязательные: …
         Ничего не скачаю, пока не напишете «утверждаю 1, 2, 4».

Аудитор: утверждаю 1, 2, 4 плюс Инструкция НБРБ № 38

Агент:   [select + extra_titles + download + index]
         Скачано 5, 1 не найден. Можно «скачай», «документы», «саммари».

Аудитор: саммари
         Какой срок возврата валютной выручки по аренде нерезиденту?

Агент:   Word на 6–10 стр. со ссылками [n]
         Ответ по норме + цитаты из библиотеки кейса
```

Почему так, а не React:

- Open WebUI уже умеет чат, файлы, цитаты, Knowledge, auth. Второй UI = второй продукт до планки Cursor.
- HITL хорошо живёт в чате, если tool возвращает структурированный список и **не идёт дальше без id**.
- Лабораторный Vite сейчас полезен, чтобы отладить API. Он не должен обрастать «настоящим» дизайном.

Если чат окажется плохим для галочки «выбрать 7 из 15»:

| План Б | Когда | Свой код |
|---|---|---|
| Pipeline со стадией `await user` | список длинный, нужен явный шаг | низкий |
| Одна страница Streamlit/HTMX только на библиотеку | чат совсем не заходит | низкий |
| Оставить React-мастер | только если Б не сработал | высокий — значит, сознательно платим |

План Б выбираем **после** первой недели tools в Open WebUI, не заранее.

Свой `POST /api/v1/cases/{id}/knowledge/ask` — **основной** ответ аудитора в продукте: Pipe вызывает его после скачивания библиотеки. Коллекция Open WebUI Knowledge — опциональный дубль `.txt` (если задан API-ключ). Дублировать RAG-чат в React нельзя.

## 4. Audit Tool Server — что внутри, чего нет

Сервер — не «ещё один RAG». Это **система записи проверки**.

### Есть (и оставляем)

- кейс: `inspection_name`, keywords, period, статус;
- propose → select (HITL) → download (manual URL / known_sources / SearXNG);
- extract HTML/PDF → текст, чанкер по статьям, саммари Word (`саммари` в чате);
- sync очищенного `.txt` в коллекцию Open WebUI;
- файлы кейса на диске.

### Есть, но не раздувать

- свой векторный индекс и `/knowledge/ask` — для контроля нарезки по «Статья N» и тестов качества. Не делать из этого второй чат.
- React-мастер — не развивать.

### Появится, потому что готового нет

| Модуль | Почему свой | Чего не пишем вокруг |
|---|---|---|
| **Case store** | Контур проверки, статусы, кто утвердил список | Не пишем админку кейсов. Список кейсов — tool + папки / позже SQLite |
| **NPA library** | Allowlist РБ, known_sources, политика «не искать клиентским текстом» | Не пишем краулер pravo.by |
| **Ingest НПА** | Статья/пункт важнее дефолтного сплиттера Open WebUI | Не пишем свою vector DB, если хватает markdown `## Статья` + Open WebUI |
| **Evidence store** | Выгрузки клиента ≠ НПА. Отдельные пути, отдельные tools | Не RAG по Excel |
| **Tests** | Процедура, выборка, критерий ok/finding — доменная модель | Не UI конструктора тестов |
| **Working papers** | Слепок: норма + факт + вывод, шаблон банка | Не WYSIWYG-редактор |
| **Rules** | Детерминированные проверки (курсы, лимиты) | Не «обучаем классификатор» |
| **Audit trail** | file, chunk, url, tool call, кто утвердил | Не отдельный SIEM |

### Хранение v1 (без овердизайна)

Сейчас папки, без БД — это правильно, пока один аудитор / одна машина:

```
data/audit_cases/{case_id}/
  case.json              состояние кейса (система записи)
  manifest.json
  knowledge_raw/         первоисточники НПА
  knowledge_text/        очищенный текст
  summaries/
  knowledge_index.json
  library.zip
  evidence/              позже: выгрузки клиента (не в Knowledge НПА)
  tests/                 позже
  wp/                    позже: черновики .docx / .md
  trail/                 позже: jsonl вызовов tools и цитат
```

SQLite появится, когда понадобятся поиск по кейсам, пользователи, неизменяемый trail. Не раньше. Не Postgres «на вырост».

## 5. Потоки данных

### 5.1 Собрать библиотеку НПА

```
название + keywords
  → LLM propose (Ollama)
  → аудитор утверждает document_ids          ← HITL, без этого download нет
  → URL: manual → known_sources → SearXNG
  → knowledge_raw + extract → knowledge_text
  → саммари на диск + Word на 6–10 стр. (команда «саммари»)
  → нормализация markdown (## Статья N)
  → Open WebUI Knowledge коллекция npa-{case_id}
```

Клиентские данные в SearXNG **не передаются**.

### 5.2 Спросить норму

```
вопрос в Open WebUI
  → hybrid retrieval по коллекции кейса
  → RAG-шаблон: только фрагменты, цитируй, не выдумывай, не РФ/IFRS
  → ответ + citations
  → (опционально) сервер пишет trail: file, chunk, score
```

Веб-поиск в этом потоке **выключен**. SearXNG — только добыча в библиотеку.

### 5.3 Спросить факт (план)

```
вопрос «сколько начислено аренды за период»
  → tool evidence_sql (DuckDB по файлам в evidence/)
  → не retrieval по таблице
  → цифра + имя файла + запрос
```

### 5.4 Черновик теста / WP (план)

```
фаза pipeline
  → server: список утверждённых норм + факты из tools
  → LLM черновик процедуры / WP
  → аудитор правит в чате или в .docx
  → статус «черновик», не «утверждено»
```

---

## 6. Норма ≠ факт

Две вселенные. Смешивать в одной Knowledge-коллекции нельзя.

| | Норма | Факт |
|---|---|---|
| Что | НПА, внутренние политики | Выгрузки, договоры, обороты |
| Где | `knowledge_*`, коллекция `npa-{id}` | `evidence/`, DuckDB |
| Как отвечает модель | RAG + цитата статьи | tool / SQL / pandas |
| Риск ошибки | галлюцинация статьи | «похожий ряд в Excel» |

Внутренние политики банка — ближе к норме (можно отдельная коллекция `policy-{id}`), не к факту.

## 7. Коробка (как это вообще поставляется)

Продукт = **репозиторий compose + seed**, не «клонируйте backend и поставьте Ollama сами».

```
compose.yaml
  open-webui          :3000  единственный URL за Caddy
  audit-tool-server   :8100  внутренний
  searxng             :8080  внутренний
  ollama              :11434 внутренний
  caddy               :443   audit.local

seed/
  openwebui/
    rag_template.txt
    system_prompt_auditor.txt
    functions/          create_case, propose, select, download, …
    pipelines/          audit_phases.py
  searxng/settings.yml  allowlist доменов РБ
  models.txt            qwen chat + qwen embedding (офлайн-бандл)
```

Засев Open WebUI — часть продукта. Без него аудитор получит MiniLM, `num_ctx=2048` и галлюцинации. Это описано в [RAG_для_разработчика.md](RAG_для_разработчика.md); в коробке эти настройки **уже стоят**.

Air-gap: образы и веса моделей едут файлами, не качаются с Hugging Face в банке.

## 8. Качество retrieval (не изобретаем)

Источник истины по RAG — [RAG_для_разработчика.md](RAG_для_разработчика.md). Архитектурно фиксируем:

1. В Knowledge заливаем **очищенный текст** с заголовками статей, не сырой HTML.
2. Embedding — та же Ollama-модель, что при ingest. Не MiniLM.
3. Hybrid + rerank. Чанк ~1500–2000, контекст модели 32k+.
4. Сначала классический RAG (chunks всегда в промпте). Native tools — когда модель стабильно вызывает search.
5. После каждой смены настроек — четыре золотых теста из RAG-дока.

Свой чанкер по `ARTICLE_RE` ценен. Дешёвый путь в коробку: превращать текст в markdown `## Статья N` и отдать сплиттер Open WebUI, а не поднимать вторую vector DB.

## 9. Доверие и контур

- Ollama, Open WebUI, SearXNG, данные кейса — на машине/контуре банка.
- Allowlist поиска железно в SearXNG **и** в сервере (defense in depth).
- Tools, которые трогают `evidence/`, не имеют права ходить в интернет.
- Модель не ставит суждение и не подписывает WP.
- Trail: что скачали, из какого URL, какой чанк ушёл в ответ, какой tool с какими аргументами.

---

## 10. Анти-цели архитектуры

Чтобы не расползтись, пока «качество как Cursor» ещё не достигнуто:

- не форкать Open WebUI;
- не писать SPA «на все шаги проверки»;
- не строить микросервисы (отдельный ingest-service, отдельный wp-service);
- не заводить Kubernetes;
- не класть клиентский Excel в Knowledge «на всякий случай»;
- не делать веб-поиск дефолтом чата;
- не менять чат-модель, пока не пройдены золотые тесты RAG.
