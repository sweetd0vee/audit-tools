# Идеи

Бэклог, а не обязательства. В спринт идея попадает, только если её можно сделать **готовым инструментом + тонким клеем** и она не спорит с [PLAN.md](PLAN.md) (после v0.0.1).

Сгруппировано: ядро опыта → качество как у Cursor → домен аудита → поставка → сознательно позже / нет.

v0.0.1 уже закрывает: один персонаж «Аудитор» в чате, HITL на НПА и гипотезах, саммари / программу / мнение / заключение, ручную ссылку (`к N url …`). Ниже — то, чего в демо ещё нет.

---

## 1. Ядро опыта (коробка должна так ощущаться)

### Один персонаж «Аудитор»
Не выбор модели из списка Ollama. Одна кнопка New Chat: промпт, tools, RAG, `num_ctx` уже стоят. Как дефолтная модель в Cursor.

### Проверка как «workspace»
Кейс = чат (или папка чатов) + коллекция Knowledge + `evidence/`. Команда «открой проверку аренды-2025» переключает контур. Без своего dashboard, если хватает `#коллекция` и tool `open_case`.

### Пакеты типовых проверок
Готовый набор, не пустой кейс:

- keywords и типичный список НПА (known_sources уже заполнен);
- золотые вопросы «спросить закон»;
- шаблон тестов и WP;
- примеры SQL к типовой выгрузке.

Пилот: **аренда коммерческой недвижимости**. Потом: валютный контроль, кредиты юрлиц, связанные стороны, касса/подотчёт.

Это контент, не код. Сильный рычаг «коробочности».

### Команды в чате, не меню
`/library` `/ask-norm` `/sql` `/tests` `/wp` — если Open WebUI это умеет через prompts/commands. Иначе те же verbs через system prompt. Не рисовать ленту кнопок в React.

### Саммари акта как «не читай кодекс»
Уже почти есть. Идея продукта: в начале кейса агент кладёт 5–7 карточек «зачем этот акт в проверке» со ссылкой на файл. Читать глазами 2 экрана, не 200 страниц. Карточки — markdown в кейсе, не новая сущность UI.

### Ручная ссылка — первый класс
Аудитор часто *знает* URL на pravo.by. Вставить ссылку должно быть проще, чем надеяться на SearXNG. Идея: tool `add_npa_url` и промпт «если знаете ссылку — сразу дайте».

## 2. Качество ответа (то, чем Cursor отличается от «просто LLM»)

### Золотой набор вопросов
20–30 пар вопрос–ожидание на каждый пакет проверки. CI или скрипт `eval_rag.py` после смены embedding/chunk. Без этого RAG крутят «на глаз» и ломают доверие.

### Отказ как фича
Ответ «в утверждённой библиотеке этого нет» важнее гладкого абзаца. Показывать, *где* искали (имена актов). Калибровать промптом и порогом rerank, не дописыванием «уверенности %».

### Цитата = файл в кейсе
Клик по citation открывает тот же `.txt`/PDF, что лежит в `knowledge_raw`. Если Open WebUI уже так делает — ничего не пишем. Если нет — tool `open_source(file, article)` возвращает кусок текста.

### Двухмодельный контур (когда железа хватает)
Маленькая модель: классификация «это вопрос к норме / к факту / к процедуре» и выбор tool. Большая: ответ по фрагментам. Не делать, пока одна сильная модель стабильно вызывает tools.

### Hybrid обязан для «ст. 625»
Идея не новая, но продуктовая: в подсказках аудитору явно писать «можно по номеру статьи». BM25 — часть качества коробки, не «настройка админа».

### Reindex без шаманства
Смена embedding = кнопка/tool «переиндексировать коллекцию кейса», а не инструкция из восьми шагов. Пока можно документировать Admin → Reindex в seed-доке; потом — если API позволит, обернуть tool.

### Не смешивать редакции
Идея: в метаданных чанка дата редакции / URL. В ответе модель называет акт полностью. Позже: предупреждение «в кейсе две редакции ГК».

## 3. Домен внутренней проверки

### Программа проверки из библиотеки

**Есть:** команда `программа проверки` отдаёт Word-черновик — таблицу «вопросы, подлежащие аудиту» (число пунктов задаёт аудитор: `программа проверки 8`). Это не HITL по отдельным тестам и не утверждённая программа СВА.

Осталось: `propose_tests` → `select_tests` и шаблон WP. Не плодить второе SPA «конструктор программы».

### Выборка без магии
MUS / случайная / сплошная как **код** (numpy/pandas) + параметры от аудитора. Модель не «выбирает 25 договоров, которые ей показались странными», если аудитор не попросил judgmental sample явно.

### Регистр находок
Таблица в кейсе (`findings.jsonl` или лист xlsx): факт, критерий, норма, риск, черновик формулировки. UI = файл + tool `add_finding`. Выгрузка в Excel, которым отдел уже живёт.

### Working paper как Word банка
Не свой редактор. Слоты: цель теста, норма (цитата), процедура, выборка, факт, вывод, вложения. Статус `draft`. Идея качества: в WP автоматически попадает id чанка и путь к evidence.

### Сверка норма ↔ факт
Шаблон хода: «вот пункт инструкции — какой столбец выгрузки это доказывает?». Модель предлагает маппинг, аудитор подтверждает, дальше rule/SQL.

### Rules-каталог на YAML
Примеры, не платформа:

- курс НБРБ на дату vs курс в договоре;
- срок возврата валютной выручки vs дата поступления;
- лимит сделки / связанность по ИНН (если поле есть).

Каждое rule — функция + тест на фикстуре. LLM только объясняет fail человеческим языком.

### Внутренние политики банка
Вторая коллекция Knowledge, не интернет. Тот же HITL на «какие политики в скоупе». Allowlist сюда не относится — файлы кладёт аудитор.

### Обновление НПА
v1: tool `refresh_document` по URL. Идея позже: сверка hash/даты с pravo.by по крону. Не начинать с краулера.

### Экспорт кейса
Zip уже почти есть для библиотеки. Идея продукта: «сдать папку проверки» — НПА + саммари + trail + черновики WP + findings, без весов моделей и без чужих кейсов.

## 4. Поверхности кроме чата (только если чат не тянет)

### MCP-сервер над Audit Tool Server
Тот же API, что tools Open WebUI. Тогда разработчик (и аудитор в Cursor) ведёт проверку из IDE. Свой код — тонкая обёртка. Не конкурирует с коробкой, а расширяет её. Имеет смысл **после** стабильных tools в WebUI.

### Continue.dev
Править YAML rules и шаблоны WP как код. Не для аудитора-пользователя коробки v1.

### Одна форма Select
Если HITL списка НПА в чате провалится: Streamlit/HTMX на 1 экран. Идея: генерировать форму из `propose`, POST в тот же `/select`. Запрещено превращать это в «портал проверки».

### n8n / Dify
Имеет смысл только если Pipelines Open WebUI окажутся неудобны. Иначе — лишний движок в коробке.

## 5. Поставка и контур банка

### Офлайн-бандл
Образы Docker + файлы моделей Ollama на диске. Скрипт `import`. Без этого в контуре банка коробка не взлетит.

### Health-экран без своего фронта
Caddy + Open WebUI. Идея: tool `health` или страница `/` сервера, которую WebUI показывает при старте: Ollama жив, embedding жив, SearXNG жив, диск кейсов доступен.

### Политика сети
Два режима: `airgap` (SearXNG выключен, только manual URL и known_sources) и `allowlist`. Переключатель env, не код.

### Модель поменьше как fallback
Если 27B не влезает: в compose profile `gpu-light`. Качество RAG тогда упирается в retrieval ещё сильнее. Не плодить «оптимизатор промптов», сначала измерить eval.

### Логи без клиентских полей
Trail tools: аргументы SQL можно хранить, строки выборки — нет или маскировать. Идея политики, не фича «для красоты».

## 6. Идеи, которые звучат хорошо и вредят продукту

Их легко начать и невозможно довести до качества Cursor.

| Идея | Почему нет (сейчас) |
|---|---|
| Свой чат / свой Knowledge UI | Дубль Open WebUI, вечный второй сорт |
| «Портал аудитора» на React со всеми шагами | Платформа вместо коробки |
| RAG по Excel и договорам в одной куче с ГК | Галлюцинации фактов |
| Автоматическое юридическое заключение | Нельзя по инварианту продукта |
| Поиск по всему интернету «для полноты» | Утечки и чужая юрисдикция |
| Форк Open WebUI «чуть подкрутить UX» | Навсегда отстанем от апстрима |
| Мультиагенты (исследователь, скептик, писатель) | Сначала один агент с HITL и tools |
| Fine-tune на НПА | RAG + нормальный чанкер дешевле и честнее |
| Облачный SaaS | Ломает локальность клиентских данных |
| Канбан согласования проверки | Это СЭД банка, не наш продукт |
| Распознавание сканов «на всякий случай» в 0.0.x | OCR — отдельная боль; сначала текстовые HTML/PDF с pravo.by |
