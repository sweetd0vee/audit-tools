# План действий

От лабораторного API к **коробке**. Каждый этап должен либо выкинуть свой код, либо дать аудитору законченный кусок работы. Не параллелим «ещё один UI» и «ещё одну базу».

Опора: [VISION.md](VISION.md), [ARCHITECTURE.md](ARCHITECTURE.md).

---

## Правило отбора работ

Прежде чем писать что-то своё, три вопроса:

1. Это уже есть в Open WebUI / Ollama / SearXNG / DuckDB / Word-шаблоне?
2. Если нет — хватит ли tool-скрипта на 50–150 строк, который дергает наше API?
3. Если нет — это домен проверки (кейс, HITL, НПА РБ, trail)? Тогда пишем в Audit Tool Server.

Нет → не делаем. Особенно: экраны, админки, второй RAG.

---

## Сейчас (факт)

Аудиторский поток библиотеки НПА живёт в чате. Как пользоваться: [AUDITOR.md](AUDITOR.md).

- FastAPI: кейс, propose / select / download, extract, ask, саммари Word, sync в Open WebUI;
- Pipe «Аудитор» (`seed/openwebui/functions/audit_agent.py`): фазы и HITL в коде, download только после «утверждаю»;
- React-мастер шагов 1–2 на Vite — **заморожен, не развиваем**;
- `docker-compose.yml` поднимает SearXNG + Open WebUI + backend; frontend только `--profile lab`;
- засев Open WebUI (промпт, RAG-шаблон, Pipe) — Admin ещё руками, см. [`seed/openwebui/AGENT.md`](../seed/openwebui/AGENT.md);
- запасной native Tools (`audit_case.py`) есть, для продукта не основной путь (35B ломает HITL);
- данных клиента, тестов, WP, полных агентных фаз проверки — нет.

Как сесть писать на этой неделе: [START.md](START.md).

- [ ] Составить список «не делать» из §10 архитектуры и не нарушать его без явного решения.

Выход: можно отказывать себе в фичах.

## Этап 1 — Коробка из того, что уже есть  
*главный рычаг качества на ближайшие недели*

Цель: `compose up` (или один скрипт на Windows) → открыл URL → чат с уже настроенным RAG. Без вики из шести сервисов.

- [x] Корневой `compose.yaml`: Open WebUI, Ollama, SearXNG, Audit Tool Server; frontend — profile `lab`.
- [x] `seed/openwebui`: RAG-шаблон аудитора, system prompt; hybrid/embedding в compose env (на чистом volume).
- [ ] `.env.example` на корне: модели, порты, пути данных.
- [x] Документ «как аудитор ведёт проверку в чате»: [AUDITOR.md](AUDITOR.md).
- [ ] Документ «поставил → работает» на одну страницу (образы, pull моделей). Для банка — пометка про офлайн-бандл образов/весов.
- [ ] Прогнать четыре золотых теста RAG из [RAG_для_разработчика.md](RAG_для_разработчика.md) на одной инструкции НБРБ.

Выход: стенд собирается как продукт. Это уже ближе к Cursor, чем любой новый экран.

Не делать на этом этапе: новый фронт, Postgres, агент на 7 фаз.

## Этап 2 — Аудитор живёт в чате, не в Vite  
*проверка гипотезы «фронт не нужен»*

Цель: полный поток библиотеки НПА из Open WebUI. React больше не нужен для демо.

- [x] Агент в чате — Pipe, не набор native tools: create → propose → HITL select → download → index; ask и brief в том же диалоге.
- [x] Жёсткий HITL: download не вызывается без `document_ids`, которые аудитор явно утвердил (`утверждаю 1, 2`).
- [x] System prompt / правила Pipe: фазы в коде, «не выдумывай статьи», клиентский текст в SearXNG не уходит.
- [x] Sync в Knowledge после download — часть approve-ветки Pipe (если задан `OPENWEBUI_API_KEY`).
- [x] Сценарий аренды в чате: список, ручной URL (`к N url …`), повтор `скачай`, `саммари`, вопрос с цитатой. Где ломается — длинный список номерами, обрезанный URL, 403 SearXNG (лечится known_sources / ручной ссылкой).
- [ ] Засев Pipe при `compose up` без ручной вставки в Admin.

Решение по фронту после этого этапа, не до:

| Наблюдение | Решение |
|---|---|
| Аудитор утверждает список в чате без боли | `frontend/` заморозить, потом удалить |
| Список из 15 актов неудобно галочками в тексте | Pipeline со стадией подтверждения или одна HTMX/Streamlit-страница **только** на select |
| Всё равно «хотим свой портал» | Отдельное продуктовое решение, это уже другой объём |

Параллельно: не развивать React (новые шаги 3–6 туда не класть).

Выход: демо продукта = вкладка браузера с Open WebUI.

## Этап 3 — Качество НПА, не «ещё поиск»

Цель: цитата стабильно из нужной статьи, отказ если статьи нет. Это ядро доверия, как «модель видит *этот* файл» у Cursor.

- [ ] Перед sync: нормализация `.txt` → markdown с `## Статья N` / `## Пункт N`, заголовок акта, URL, дата.
- [ ] Не плодить вторую vector DB, пока markdown + hybrid не исчерпаны.
- [ ] Саммари акта — файл в кейсе и/или первое сообщение в Knowledge, не отдельное SPA.
- [ ] Eval: 20–30 золотых вопросов по 3–4 типовым актам (есть в тексте / нет в тексте / поиск по номеру статьи / перефраз). Гонять после смены embedding и chunk.
- [ ] Trail минимум: в `case.json` или `trail/*.jsonl` — какие file_id ушли в Open WebUI.

Выход: можно показать службе внутреннего аудита ответ с цитатой и не краснеть.

## Этап 4 — Кейс как система записи (чуть больше, чем папки)

Цель: несколько проверок на одной машине, не потерять состояние, не строить ERP.

- [ ] Список кейсов: `GET /cases` уже почти есть — tool `list_cases` + в чате «открой кейс X» (привязать Knowledge).
- [ ] Оставить файловый store. SQLite — только если больно искать по кейсам или писать trail.
- [ ] Статусы кейса не расширять до BPM (не «согласовано начальником отдела»). v1: created → proposed → selected → ready.
- [ ] Ручной URL и known_sources — первый класс, SearXNG — запас. Поисковики его банят; коробка не должна «умирать без интернета-поиска», если аудитор вставил ссылку pravo.by.

Выход: аудитор ведёт 2–3 проверки, не путая коллекции Knowledge.

## Этап 5 — Данные клиента без RAG по Excel

Цель: вопрос «сколько» идёт через код. Свой аналитический UI не пишем.

- [ ] Каталог `evidence/` в кейсе. Загрузка: Files Open WebUI **в кейс через tool** или drop в папку. Не в коллекцию `npa-*`.
- [ ] Tool `evidence_sql`: DuckDB `read_xlsx` / csv, лимит строк в ответе, в trail — запрос и имя файла.
- [ ] Запрет: этот tool не вызывает SearXNG и не пишет в Knowledge НПА.
- [ ] 2–3 типовых запроса-примера в system prompt (сумма, период, группировка).

Выход: норма и факт отвечают разными механизмами. Архитектурный инвариант соблюдён.

## Этап 6 — Черновики тестов и WP, не «генератор отчёта»

Цель: ускорить бумагу, не подписать её за аудитора.

- [ ] Модель данных теста: цель, критерий, источник нормы (id акта + статья), выборка, шаги, ожидаемый ok / finding.
- [ ] Tool `propose_tests` → HITL `select_tests` (как с НПА).
- [ ] Шаблон WP банка в `seed/templates/*.docx` (норма / факт / вывод / ссылка на файл). Заполнение через python-docx. Статус всегда `draft`.
- [ ] Pipeline-фаза: «предложи тесты» / «собери черновик WP по тесту N». Логика в сервере, не в pipeline.

Выход: аудитор копирует черновик в свой контур рабочей документации, а не в наш «портал WP».

---

## Этап 7 — Rules там, где LLM врать дороже всего

Цель: курсы, лимиты, признаки — детерминированно.

- [ ] Простые rules как код или YAML: вход (поля evidence), выход (pass/fail + explanation).
- [ ] Tool `run_rule`. Модель не пересчитывает курс «примерно».
- [ ] 1–2 rules на пилотную тему (например аренда/валюта), не фреймворк на 40 правил.

Выход: пайплайн умеет «сначала rule, потом текст».

---

## Этап 8 — Полировка коробки (ощущение продукта)

Цель: как Cursor — мнение, скорость, предсказуемость, а не новые сущности.

- [ ] Одна кастомная модель в Open WebUI: «Аудитор» с Knowledge-паттерном, промптом, tools. Аудитор не выбирает между 15 моделями.
- [ ] Пакет пилотной проверки (аренда): keywords, known_sources, золотые вопросы, шаблон WP. См. [IDEAS.md](IDEAS.md).
- [ ] Инсталлятор/скрипт: проверка GPU/RAM, pull моделей, healthcheck всех контейнеров, сообщение «откройте http://…».
- [ ] Ошибки по-человечески: SearXNG 403 → «вставьте URL с pravo.by», пустой extract → «файл не текст, приложите иначе».
- [ ] Выкинуть или вынести из коробки лабораторный фронт.

Выход: можно давать человеку без доступа к репозиторию.

## Что сознательно не в плане v1

- Свой дизайн-систему и SPA.
- Мультипользовательский workflow согласования (четыре глаза — идея на потом).
- Облако, мультитенант, биллинг.
- Форк Open WebUI.
- Автообновление всех НПА с pravo.by по крону (сначала ручной re-download по кейсу).
- IDE-агент (Continue) — после того, как чат стабилен.
- Kubernetes, отдельный векторный кластер, Kafka.

## Порядок, если времени мало

Если резать scope, порядок ценности такой:

1. Этап 1 — коробка и засев RAG  
2. Этап 3 — цитаты и eval (можно частично параллельно с 1)  
3. Этап 2 — tools в чате, решение по фронту  
4. Этап 5 — DuckDB  
5. Этап 6 — WP-шаблон  
6. Остальное

Писать React-портал при неготовой коробке — самый дорогой способ не получить продукт.

## Критерии «мы близко к Cursor»

Не «есть GPT в чате», а:

- [ ] Человек без этого репо поднимает систему одной командой и задаёт вопрос по акту с цитатой.
- [ ] На вопросе, которого нет в библиотеке, модель отказывается, а не сочиняет статью.
- [ ] Список НПА нельзя скачать без утверждения аудитора.
- [ ] Excel клиента не всплывает в ответе про закон.
- [ ] Нет второго окна «настоящего UI», без которого нельзя работать.
- [ ] Повторная проверка той же темы начинается с пакета, а не с пустого промпта.

Идеи сверх каркаса — в [IDEAS.md](IDEAS.md), в спринт попадают только если не спорят с этим планом.
