# План действий

От лабораторного API к **коробке**. Каждый этап должен либо выкинуть свой код, либо дать аудитору законченный кусок работы. Не параллелим «ещё один UI» и «ещё одну базу».

Опора: [VISION.md](VISION.md), [ARCHITECTURE.md](ARCHITECTURE.md). Как сесть писать: [START.md](START.md).

---

## Правило отбора работ

Прежде чем писать что-то своё, три вопроса:

1. Это уже есть в Open WebUI / Ollama / SearXNG / DuckDB / Word-шаблоне?
2. Если нет — хватит ли tool-скрипта на 50–150 строк, который дергает наше API?
3. Если нет — это домен проверки (кейс, HITL, НПА РБ, trail)? Тогда пишем в Audit Tool Server.

Нет → не делаем. Особенно: экраны, админки, второй RAG.

## Сейчас (факт, август 2026)

Аудиторский поток живёт в чате Open WebUI, модель **Аудитор** (Pipe). Как пользоваться: [GUIDE.md](GUIDE.md).

**Закрыто в коде**

- FastAPI: кейс (`created → proposed → selected → downloading → ready / failed`), propose / select / download, extra_titles, manual URL, known_sources, SearXNG по allowlist, extract, индекс, ask, sync Open WebUI.
- Word: обзор актов (`саммари`), конспект из знаний модели (`саммари total`), программа проверки (`программа проверки`). Стримы SSE, повтор `… заново`.
- Pipe (`seed/openwebui/functions/audit_agent.py` v0.2.1): фазы **кодом**, HITL — download только после «утверждаю». Вопрос к базе — только с префиксом `вопрос …`. Иначе обычный диалог (`POST /api/v1/chat`), не RAG.
- `GET /cases`, в чате `кейсы` / `статус`. Файловый store, без БД.
- `docker-compose.yml`: SearXNG + Open WebUI + backend; frontend только `--profile lab`.
- Запасной native Tools (`audit_case.py`) есть, для продукта не основной путь (27B ломает HITL).
- Тесты backend: extra_titles, download URLs, brief, openwebui client.

**Ещё руками / нет**

- Засев Pipe при `compose up` — Admin вставляет функцию вручную ([AGENT.md](../seed/openwebui/AGENT.md)).
- Данных клиента, тестов, WP, rules, неизменяемого trail — нет.
- Eval RAG (золотые вопросы) — нет.
- Нормализация `.txt` → markdown `## Статья N` перед sync — нет (чанкер по «Статья N» на сервере уже есть).

Гипотеза «фронт не нужен для HITL» на текущем контуре **подтверждена**: список утверждается номерами в чате. `frontend/` остаётся замороженным.

## Этап 1 — Коробка из того, что уже есть

Цель: `compose up` → открыл URL → чат с уже настроенным RAG. Без вики из шести сервисов.

- [x] Корневой compose: Open WebUI, SearXNG, Audit Tool Server; Ollama на хосте; frontend — profile `lab`.
- [x] `seed/openwebui`: RAG-шаблон, system prompt; hybrid/embedding в compose env (на чистом volume).
- [x] Документ «как аудитор ведёт проверку в чате»: [GUIDE.md](GUIDE.md), шпаргалка [AUDITOR.md](AUDITOR.md).
- [x] `backend/.env.example`: модели, Ollama, SearXNG, Open WebUI.
- [ ] `.env.example` на **корне** compose (порты, модели) — дубль для человека без захода в `backend/`.
- [ ] Документ «поставил → работает» на одну страницу (образы, pull моделей, офлайн-бандл для банка).
- [ ] Прогнать четыре золотых теста RAG из [RAG_для_разработчика.md](RAG_для_разработчика.md) на одной инструкции НБРБ.

Выход: стенд собирается как продукт.

Не делать на этом этапе: новый фронт, Postgres, агент на 7 фаз проверки.

## Этап 2 — Аудитор живёт в чате, не в Vite

Цель: полный поток библиотеки НПА из Open WebUI. React больше не нужен для демо.

- [x] Агент в чате — Pipe, не набор native tools: create → propose → HITL select → download → index.
- [x] Жёсткий HITL: download не вызывается без `document_ids`, которые аудитор явно утвердил (`утверждаю 1, 2`).
- [x] Фазы в коде: «не выдумывай статьи»; клиентский текст в SearXNG не уходит.
- [x] Sync в Knowledge после download — если задан `OPENWEBUI_API_KEY` (или сессионный токен).
- [x] Сценарий аренды: список, `плюс …`, ручной URL (`к N url …`), повтор `скачай`, `саммари`, `вопрос …` с цитатой.
- [x] Word-программа проверки и `саммари total` в том же диалоге.
- [x] Явный префикс `вопрос` отделяет RAG от обычного чата (иначе 27B путала норму и болтовню).
- [ ] Засев Pipe при `compose up` без ручной вставки в Admin.

Решение по фронту **принято**: `frontend/` заморожен. План Б (HTMX только на select) не открываем, пока номера в чате не начнут ломаться на реальных аудиторах.

Выход: демо продукта = вкладка браузера с Open WebUI. Почти достигнуто; мешает только ручной засев Pipe.

## Этап 3 — Качество НПА, не «ещё поиск»

Цель: цитата стабильно из нужной статьи, отказ если статьи нет. Это ядро доверия, как «модель видит *этот* файл» у Cursor.

- [x] Свой индекс + `/knowledge/ask`; чанкер режет по «Статья / Глава N».
- [x] Саммари акта — файл в кейсе (`summaries/`) и Word по команде, не SPA.
- [ ] Перед sync: нормализация `.txt` → markdown с `## Статья N` / `## Пункт N`, заголовок акта, URL, дата.
- [ ] Не плодить вторую vector DB, пока markdown + hybrid не исчерпаны.
- [ ] Eval: 20–30 золотых вопросов по 3–4 типовым актам (есть в тексте / нет в тексте / поиск по номеру статьи / перефраз). Гонять после смены embedding и chunk.
- [ ] Trail минимум: в `case.json` или `trail/*.jsonl` — какие file_id ушли в Open WebUI, какой чанк в ask.

Выход: можно показать службе внутреннего аудита ответ с цитатой и не краснеть.

## Этап 4 — Кейс как система записи (чуть больше, чем папки)

Цель: несколько проверок на одной машине, не потерять состояние, не строить ERP.

- [x] Список кейсов: `GET /api/v1/cases` + в чате `кейсы` / `проверки` / `статус`.
- [x] Файловый store. Статусы: created → proposed → selected → downloading → ready / failed.
- [x] Ручной URL и known_sources — первый класс, SearXNG — запас.
- [ ] «Открой кейс X» в чате (привязать уже скачанную библиотеку к новому окну).
- [ ] SQLite — только если больно искать по кейсам или писать trail. Не раньше.

Выход: аудитор ведёт 2–3 проверки, не путая библиотеки. Частично уже так (новый чат = новый кейс; старый кейс не подхватывается фразой).

## Этап 5 — Данные клиента без RAG по Excel

Цель: вопрос «сколько» идёт через код. Свой аналитический UI не пишем.

- [ ] Каталог `evidence/` в кейсе. Загрузка: Files Open WebUI **в кейс через tool** или drop в папку. Не в коллекцию `npa-*`.
- [ ] Tool `evidence_sql`: DuckDB `read_xlsx` / csv, лимит строк в ответе, в trail — запрос и имя файла.
- [ ] Запрет: этот tool не вызывает SearXNG и не пишет в Knowledge НПА.
- [ ] 2–3 типовых запроса-примера в system prompt (сумма, период, группировка).

Выход: норма и факт отвечают разными механизмами. Архитектурный инвариант соблюдён.

`POST /api/v1/cases/{id}/knowledge/upload` уже есть — это загрузка **актов** в библиотеку, не evidence. Не использовать его для Excel клиента.

## Этап 6 — Черновики тестов и WP, не «генератор отчёта»

Цель: ускорить бумагу, не подписать её за аудитора.

- [x] Черновик **программы проверки** в Word (цель, риски, процедуры, выборка) — команда `программа проверки`. Не утверждённая программа СВА.
- [ ] Модель данных теста: цель, критерий, источник нормы (id акта + статья), выборка, шаги, ожидаемый ok / finding.
- [ ] Tool `propose_tests` → HITL `select_tests` (как с НПА).
- [ ] Шаблон WP банка в `seed/templates/*.docx` (норма / факт / вывод / ссылка на файл). Заполнение через python-docx. Статус всегда `draft`.
- [ ] Фаза: «предложи тесты» / «собери черновик WP по тесту N». Логика в сервере, не в Pipe.

Выход: аудитор копирует черновик в свой контур рабочей документации, а не в наш «портал WP».

## Этап 7 — Rules там, где LLM врать дороже всего

Цель: курсы, лимиты, признаки — детерминированно.

- [ ] Простые rules как код или YAML: вход (поля evidence), выход (pass/fail + explanation).
- [ ] Tool `run_rule`. Модель не пересчитывает курс «примерно».
- [ ] 1–2 rules на пилотную тему (например аренда/валюта), не фреймворк на 40 правил.

Выход: пайплайн умеет «сначала rule, потом текст».

## Этап 8 — Полировка коробки (ощущение продукта)

Цель: как Cursor — мнение, скорость, предсказуемость, а не новые сущности.

- [x] Одна кастомная модель в Open WebUI: «Аудитор» (Pipe). Аудитор не обязан выбирать между 15 моделями Ollama.
- [x] Ошибки скачивания в чате человеческим языком + подсказка `скачай` / `к N url …` (403 SearXNG лечится known_sources / ручной ссылкой).
- [x] Лабораторный фронт вынесен из дефолтного `up` (`--profile lab`).
- [ ] Пакет пилотной проверки (аренда): keywords, known_sources, золотые вопросы, шаблон WP. См. [IDEAS.md](IDEAS.md).
- [ ] Инсталлятор/скрипт: проверка GPU/RAM, pull моделей, healthcheck контейнеров, сообщение «откройте http://…».
- [ ] Засев Pipe без Admin.
- [ ] Выкинуть или вынести `frontend/` из репозитория коробки, когда API-лаборатория больше не нужна.

Выход: можно давать человеку без доступа к репозиторию.

- Kubernetes, отдельный векторный кластер, Kafka.

## Порядок, если времени мало

Контур чата и Word уже есть. Дальше ценность такая:

1. Этап 3 — цитаты и eval (доверие СВА).
2. Этап 1 (хвост) + этап 8 — засев Pipe, «поставил → работает».
3. Этап 4 — «открой кейс X», если путают окна.
4. Этап 5 — DuckDB / evidence.
5. Этап 6 — тесты и WP (программа Word уже есть).
6. Этап 7 — rules.

Писать React-портал при неготовой цитате — самый дорогой способ не получить продукт.

## Критерии «мы близко к Cursor»

Не «есть GPT в чате», а:

- [ ] Человек без этого репо поднимает систему одной командой (включая Pipe) и задаёт `вопрос …` по акту с цитатой.
- [ ] На вопросе, которого нет в библиотеке, модель отказывается, а не сочиняет статью. (Промпт так говорит; без eval не считаем закрытым.)
- [x] Список НПА нельзя скачать без утверждения аудитора.
- [x] Excel клиента не всплывает в ответе про закон (контура фактов нет; `вопрос` идёт только в индекс НПА).
- [x] Нет второго окна «настоящего UI», без которого нельзя работать.
- [ ] Повторная проверка той же темы начинается с пакета, а не с пустого промпта.

Идеи сверх каркаса — в [IDEAS.md](IDEAS.md), в спринт попадают только если не спорят с этим планом.
