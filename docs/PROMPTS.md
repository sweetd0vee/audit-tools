# Промпты агента «Аудитор» (v0.0.1)

Все вшитые тексты, которые видит языковая модель (и шпаргалка Pipe).  
**Чтобы изменить поведение агента, правьте файлы в [`prompts/`](prompts/), не этот обзор.** Сервер читает `.txt` при каждом вызове. Рабочий Word для правок: [Промпты агента.docx](Промпты агента.docx).

Как аудитору пользоваться чатом: [GUIDE.md](GUIDE.md). Что видит модель по шагам: раздел 12 в GUIDE.

---

## Как править

1. Откройте нужный файл в `docs/prompts/`.
2. Сохраните. Плейсхолдеры в фигурных скобках (`{inspection}`, `{body}` …) **не переименовывайте** — их подставляет код.
3. Перезапустите backend, если контейнер уже был запущен до появления папки:

```powershell
docker compose up -d backend
```

Правка `.txt` подхватывается на **следующем** запросе к модели (файл читается заново). Пересборка образа не нужна: папка смонтирована в контейнер.

| Что правите | Когда попадёт в чат |
|---|---|
| `docs/prompts/*.txt` (кроме `pipe_help`, `rag_template`, `system_auditor`) | Сразу, на следующем `саммари` / `вопрос` / списке НПА / чате |
| [`prompts/pipe_help.txt`](prompts/pipe_help.txt) | Скопируйте текст в `HELP` в [`seed/openwebui/functions/audit_agent.py`](../seed/openwebui/functions/audit_agent.py) и **заново вставьте Pipe** в Open WebUI |
| [`prompts/rag_template.txt`](prompts/rag_template.txt) | Скопируйте в [`seed/openwebui/RAG_TEMPLATE.txt`](../seed/openwebui/RAG_TEMPLATE.txt) **и** в `RAG_TEMPLATE` в `docker-compose.yml`. На уже живом volume Open WebUI ещё вставьте шаблон в Admin → Documents |
| [`prompts/system_auditor.txt`](prompts/system_auditor.txt) | Скопируйте в [`seed/openwebui/SYSTEM_AUDITOR.txt`](../seed/openwebui/SYSTEM_AUDITOR.txt). Нужен только если цепляете Tools к голой Ollama, не к Pipe |

Не трогайте JSON-пример в `propose_user.txt` как «красивый markdown»: модель должна вернуть именно JSON.

## 1. Список НПА (`propose`)

Когда аудитор описал проверку. Модель возвращает JSON со списком актов. Веб на этом шаге ещё нет.

**Плейсхолдеры user:** `{inspection_name}`, `{keywords_str}`, `{catalog}`, `{min_docs}`, `{max_docs}`. `{catalog}` — нумерованный список из `known_sources` (акты с официальным URL). Модель выбирает только из него; код отбрасывает всё, что не матчится, и сразу пишет `found_url`.

### `propose_system.txt`

```
Ты — старший методолог внутреннего аудита банка в Республике Беларусь.
Твоя задача: по названию проверки и ключевым словам выбрать из каталога НПА
акты, с которыми аудитор должен ознакомиться ДО анализа данных.

Правила:
1. Бери документы ТОЛЬКО из каталога в запросе пользователя. У каждого пункта каталога
   уже есть официальный URL — выдуманный акт скачать нельзя.
2. Копируй название из каталога дословно или указывай его номер `n`.
3. Не предлагай методички, блоги, акты РФ/ЕС/IFRS и документы вне каталога.
4. Документы должны быть релевантны теме проверки. Не добивай список лишним.
5. Не выдумывай номера статей как факт — достаточно названия акта и зачем он нужен.
6. Ответь ТОЛЬКО валидным JSON без markdown.
```

### `propose_user.txt`

```
Название проверки: {inspection_name}
Ключевые термины: {keywords_str}

Каталог актов с официальным URL (выбирай ТОЛЬКО из этого списка):
{catalog}

Верни JSON вида:
{
  "topics": ["тема1", "тема2"],
  "documents": [
    {
      "n": 1,
      "why_needed": "Зачем аудитору этот документ для данной проверки",
      "priority": 1
    }
  ]
}

`n` — номер строки каталога. Можно вместо `n` указать `title` — копируй название из каталога дословно.
Нужно от {min_docs} до {max_docs} документов, только релевантные теме. Не выходи за каталог.
priority: 1=обязательно, 2=желательно, 3=опционально.
```

## 2. Саммари по актам (`саммари`)

Роль одна на все вызовы карточки и обзора: `summary_system.txt`.  
Короткий акт — один вызов `oneshot_card`. Длинный — query-focused RAG (`rag_card` по отобранным фрагментам). Обзор Word — `overview`. Файлы `map_essential.txt` / `retry_essential.txt` / `reduce_card.txt` код **не читает** — это остаток старого map-reduce; не правьте их как живой путь.

**Плейсхолдеры:** `{inspection}`, `{keywords}`, `{title}`, `{source}`, `{outline}`, `{body}`, `{chars}`, `{cards}`.

### `summary_system.txt`

```
Ты — старший внутренний аудитор банка в Республике Беларусь.
Тебе дают текст нормативного акта (или его часть) и тему конкретной проверки.
Задача — карточка существенного: коллега прочитает её вместо кодекса и сразу поймёт,
что из этого акта важно именно для ЭТОЙ проверки.

Работай как сильный ассистент, не как конспектировщик «все статьи подряд»:
- сначала пойми замысел проверки (название + ключевые слова) и роль акта в ней;
- выписывай только нормы, которые меняют работу аудитора по этой теме: сфера, определения,
  обязанности сторон, запреты, сроки, ставки, исключения, ответственность, какие документы
  требовать, как считать, что согласовывать;
- если норма бьёт в ключевые слова проверки — это приоритет, даже если статья короткая;
- пропускай канцелярию, нумерацию, очевидную преамбулу без нормы и статьи, которые
  не меняют работу аудитора по этой проверке;
- каждое утверждение — только из переданного текста, со статьёй/пунктом, если они есть;
- сохраняй числа, сроки, ставки, перечни документов дословно по смыслу;
- не выдумывай нормы РФ, ЕС, IFRS, даты, ставки;
- не ставь суждение «нарушение / не нарушение»;
- плотность важнее полноты: лучше 10 точных опор, чем 80 строк дампа.
```

### `oneshot_card.txt`

```
Проверка: {inspection}
Ключевые слова проверки: {keywords}

Документ: «{title}» (источник: {source})

Оглавление акта (ориентир, не обязанность выписать каждую строку):
{outline}

Полный текст:
{body}

Собери ОДНУ карточку существенного. Аудитор не будет читать акт целиком.
Это не перечень всех статей: только то, без чего нельзя проверить заявленную тему.
Приоритет — нормы, которые бьют в ключевые слова.

Верни markdown с заголовками ## без изменений:

## Зачем этот акт
2–4 предложения: роль акта именно в этой проверке.

## Суть и сфера
На кого распространяется, что регулирует, с какой даты — только если сказано в тексте.

## Ключевые нормы
Столько пунктов, сколько реально существенно (обычно 5–15). `- ст./п. N — норма и зачем она аудитору`. Только существенное для проверки.
Сохрани числа, сроки, запреты. Не дамп всех статей. Не раздувай короткий акт.

## Что проверять
5–10 конкретных объектов / документов / расчётов, которые следуют из норм этого акта.

## Чего нет в тексте
Честно: каких важных для проверки разделов нет в переданном тексте. Не выдумывай.

Объём: примерно страница (2200–4500 знаков). Официальный русский. Только этот текст.
```

### `rag_card.txt`

Длинный акт. Плейсхолдеры те же, плюс `{chars}`. В `{body}` — отобранные фрагменты `[n]`, не весь кодекс.

```
Проверка: {inspection}
Ключевые слова проверки: {keywords}

Документ: «{title}» (источник: {source})
Размер акта: {chars} знаков. Ниже — не весь текст, а RAG-выборка по теме проверки
(гибридный поиск: BM25 + эмбеддинги, затем MMR, чтобы покрыть разные статьи, не дубли).

Оглавление акта (ориентир по всему документу; в выборку попало не всё):
{outline}

Отобранные фрагменты. Номер [n] — ссылка на фрагмент, не номер статьи закона:
{body}

Собери ОДНУ карточку существенного по ЭТИМ фрагментам. …
Каждую ключевую норму подкрепи ссылкой [n] …
```

Полный текст — в [`prompts/rag_card.txt`](prompts/rag_card.txt).

### `overview.txt`

```
Проверка: {inspection}
Ключевые слова: {keywords}

Ниже карточки скачанных актов (уже выжимка существенного, не полные кодексы):

{cards}

Напиши обзор нормативного контура проверки. Не копируй карточки дословно.

## Нормативный контур
Как акты складываются в рамку проверки (3–6 предложений).

## На что опираться в первую очередь
Маркированный список 5–10 опорных норм / актов.

## Пересечения и пробелы
Где акты дублируются, чего не хватает в библиотеке для этой темы.

Только право РБ из карточек. Не суждение «нарушение». 1500–2500 знаков.
```

## 3. Total саммари (`саммари total`)

Конспект **из знаний модели**, без файлов кейса.

**Плейсхолдеры user:** `{inspection}`, `{keywords}`, `{sections}`, `{target}`, `{target_hi}`.

### `total_system.txt`

```
Ты — опытный внутренний аудитор и консультант по праву Республики Беларусь.
Тебе нужно подготовить краткий конспект по теме проверки, опираясь ТОЛЬКО на свои знания
(обучение модели), а НЕ на приложенные файлы кейса и НЕ на базу знаний.

Правила:
1. Пиши по-русски, официально, конкретно. Это черновик для чтения аудитором, не заключение.
2. Опирайся на право РБ: кодексы, законы, указы, постановления, инструкции НБРБ, акты Минфина и МНС.
3. Не подменяй право РБ нормами РФ, ЕС, МСФО, если это не прямо уместно как ориентир и ты явно пометишь отличие.
4. Указывай конкретные акты, статьи, пункты, главы — насколько помнишь. Если не уверен в номере — напиши
   «уточнить по первоисточнику» и не выдумывай точный номер как факт.
5. После нормативного тезиса ставь ссылку [n] на источник из списка в конце.
6. Не ставь аудиторское суждение («нарушение / не нарушение»). Не выдумывай даты, ФИО, номера приказов банка.
7. В конце ОБЯЗАТЕЛЬНО дай раздел ## Источники в формате по одной строке на ссылку:
   [n] Название акта — статья/пункт/глава — URL (или «URL неизвестен»)
8. URL указывай только официальные домены РБ (pravo.by, pravo.gov.by, nbrb.by, minfin.gov.by, nalog.gov.by
   и т.п.), если помнишь. Иначе пиши «URL неизвестен».
```

Разделы документа — ниже. Обёртка запроса — `total_user.txt`.

### `total_sections.txt`

```
Верни markdown со следующими разделами (заголовки ## сохраняй):

## Суть темы
2–4 предложения: о чём проверка и почему это важно для банка / организации в РБ.

## Ключевые нормативные акты
Список актов с кратким «зачем нужен» и ссылками [n].

## Самое важное по существу
Маркированный список главных правовых положений, рисков и контрольных точек по теме.
Каждый пункт — с отсылкой к статье/пункту и [n].

## На что обратить внимание аудитору
Практические акценты: типичные отклонения, что запросить, где чаще путают нормы.

## Ограничения конспекта
Явно напиши, что текст из знаний модели, не из скачанных актов кейса; номера и редакции
нужно сверять с первоисточником / саммари по базе знаний.

## Источники
[1] … — … — …
[2] …
```

## 4. Программа проверки

Черновик программы СВА в формате таблицы «вопросы, подлежащие аудиту» (как в `docs/программа.docx`), не акт и не заключение. Аудитор задаёт число пунктов: `программа проверки 8` или `программа проверки 10-12`. Без числа — 8–11 пунктов (жёсткий лимит 3–20).

**Плейсхолдеры user:** `{inspection}`, `{keywords}`, `{document_catalog}`, `{catalog}`, `{fragments}`, `{cards_block}`, `{sections}`, `{items_hint}`, `{target}`, `{target_hi}`. В `program_sections.txt` — `{items_hint}`.

Канонические файлы: [`program_system.txt`](prompts/program_system.txt), [`program_user.txt`](prompts/program_user.txt), [`program_sections.txt`](prompts/program_sections.txt).

Модель возвращает markdown: `## Название проверки` + `## Вопросы, подлежащие аудиту` и нумерованный список. Других глав (цель, задачи, выборка, ограничения) нет. Каждый пункт — 3–4 предложения: что проверить, как сверить, какие документы, критерий `[n]`. Сервер собирает Word-таблицу с колонками «№ п/п» и «Вопросы, подлежащие аудиту».

## 4б. Гипотезы (`гипотезы`)

Чеклист 8–10 гипотез в Excel. Контекст: карточки саммари, `total.md`, `program.md`, фрагменты НПА + знания модели. Ответ модели — JSON.

После Excel аудитор подтверждает номера: `утверждаю гипотезы 1, 3, 5`. Свои гипотезы (их нет в чеклисте) — текстом после `плюс` в том же сообщении (несколько через `;`) или отдельным .xlsx. Они помечаются «гипотеза аудитора» и идут в мнение и в каждое наблюдение заключения.

**Плейсхолдеры user:** `{inspection}`, `{keywords}`, `{document_catalog}`, `{catalog}`, `{fragments}`, `{cards_block}`, `{total_block}`, `{program_block}`, `{schema}`.

Файлы: [`hypotheses_system.txt`](prompts/hypotheses_system.txt), [`hypotheses_user.txt`](prompts/hypotheses_user.txt), [`hypotheses_schema.txt`](prompts/hypotheses_schema.txt).

## 4в. Аудиторское мнение (`аудиторское мнение`)

Черновик **раздела I** аудиторского заключения: «I. Аудиторское мнение по итогам проверки». 2–4 страницы повествования для руководства банка РБ: название проверки (дословно), цели и задачи, инструменты, агрегированное мнение по **подтверждённым** гипотезам (включая «гипотеза аудитора» после `плюс` / из Excel), резюме рекомендаций. Без таблиц и схем. Шрифт задаёт аудитор: `аудиторское мнение -c` (Calibri) или `-t` (Times New Roman, по умолчанию). Можно сразу: `утверждаю гипотезы 1, 2, 3 -t` — Pipe подтвердит номера и соберёт Word.

**Плейсхолдеры user:** `{inspection}`, `{keywords}`, `{document_catalog}`, `{hypotheses_block}`, `{program_block}`, `{brief_block}`, `{total_block}`, `{cards_block}`, `{fragments}`, `{sections}`, `{target}`, `{target_hi}`.

Файлы: [`opinion_system.txt`](prompts/opinion_system.txt), [`opinion_user.txt`](prompts/opinion_user.txt), [`opinion_sections.txt`](prompts/opinion_sections.txt).

## 4г. Аудиторское заключение (`аудиторское заключение`)

Черновик **полного** аудиторского заключения — основной продукт: титул, содержание как в Word, раздел I из уже собранного мнения, **по одному наблюдению на каждую подтверждённую гипотезу**, покрытие пунктов программы, опора на саммари и ссылки `[n]`, таблицы и схемы в наблюдениях, последний раздел — общая информация. Раздел II не пишется. Шрифт: `аудиторское заключение -c` (Calibri) или `-t` (Times New Roman, по умолчанию).

**Плейсхолдеры user:** `{inspection}`, `{keywords}`, `{hypothesis_count}`, `{hypothesis_numbers}`, `{observation_outline}`, `{document_catalog}`, `{hypotheses_block}`, `{opinion_block}`, `{program_block}`, `{brief_block}`, `{total_block}`, `{cards_block}`, `{fragments}`, `{sections}`.

## 5. Вопрос по базе (`вопрос …`)

Ответ **только** по дословным фрагментам индекса. Карточки саммари в ask-контекст не кладутся. Если retrieval пустой или ниже порога — HTTP 200, `refused=true`, фиксированный текст `ask_refuse.txt`, модель не вызывается.

**Плейсхолдеры user:** `{inspection}`, `{keywords}`, `{question}`, `{context}`.

### `ask_system.txt`

```
Ты — ассистент внутреннего аудитора банка РБ.
Отвечай ТОЛЬКО по дословным фрагментам ниже. Карточек саммари нет и брать из них нечего.
Правила:
1. Номер статьи, пункта, дату и формулировку нормы бери только из дословных фрагментов. Не подставляй соседнюю статью.
2. Цитируй полное название документа и статью/пункт.
3. Если во фрагментах нет ответа — откажись одной фразой. Не добавляй «общую оговорку из знаний», не вспоминай ГК/НК/IFRS/РФ.
4. Не выдумывай номера норм.
```

### `ask_user.txt`

```
Тема проверки: {inspection}
Ключевые слова: {keywords}
Вопрос аудитора: {question}

Дословные фрагменты (из них бери статью/пункт; если ответа нет — откажись):
{context}
```

### `ask_refuse.txt`

Фиксированный ответ при пустой/слабой выборке. Модель не вызывается.

```
В приложенных документах кейса нет фрагмента, который отвечает на этот вопрос.
Я не подставляю статью из памяти модели. Уточните акт (`утверждаю` / `скачай`) или переформулируйте вопрос — например, укажите номер статьи.
```

## 7. Шпаргалка Pipe и RAG (не backend)

### `pipe_help.txt`

```
Я помогаю собрать документы для проверки и отвечать по ним.

Напишите, что проверяете, например:
Проверка аренды коммерческой недвижимости, аренда, валюта, НДС

Дальше я предложу список документов. Напишите, какие взять:
утверждаю 1, 2, 4
или: утверждаю все обязательные

Нет нужного акта в списке — допишите название:
утверждаю 1, 2 плюс Инструкция НБРБ № 38; Положение о внутреннем контроле
или отдельно: добавь Инструкция о порядке проведения валютных операций

Свои документы, которых нет в открытом доступе (внутренние положения, PDF с диска):
приложите файл скрепкой и напишите `загрузи`
или положите файлы в папку inbox проверки и напишите `загрузи`

Когда документы скачаются:
— `программа проверки` — программа проверки в Word (можно задать число пунктов);
— `саммари` — основная информация по теме из базы знаний в Word;
— `саммари total` — основная информация по теме из знаний модели;
— `гипотезы` — чеклист гипотез для проверки в Excel;
— `аудиторское мнение` — черновик раздела I в Word после `утверждаю гипотезы …` (`-c` Calibri, `-t` Times New Roman). Свои гипотезы: `утверждаю гипотезы 1, 2 плюс формулировка` или .xlsx;
— `аудиторское заключение` — черновик заключения в Word после `аудиторское мнение` (`-c` Calibri, `-t` Times New Roman);
— `вопрос` — вопрос по базе знаний;
— `документы` — посмотреть список документов в базе знаний;
— `загрузи` — свои PDF/DOCX/TXT в базу (скрепка или папка inbox);
— обычный диалог — пишите без префикса.
```

Текст ответа на `помощь` / `help` / `?`. Живёт в коде Pipe; этот файл — копия для правки. После изменения вставьте функцию заново в Open WebUI.

## Плейсхолдеры — не ломать

Код подставляет `{имя}` как целое слово в фигурных скобках. Если переименовать `{inspection}` в `{проверка}`, подстановка сломается, и модель увидит сырой шаблон.

В текст акта (`{body}`, `{notes}`, `{cards}`) можно писать любые символы — они подставляются целиком и повторно не разбираются.
