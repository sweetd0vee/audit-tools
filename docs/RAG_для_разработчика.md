# RAG для разработчика

Как работает Retrieval-Augmented Generation, как он устроен в Open WebUI, и что нужно знать, чтобы собрать базу знаний по НПА и дать аудитору возможность спрашивать документы, а не читать их целиком.

Документ рассчитан на разработчика, который уже поднимает локальный стек: **Open WebUI + Ollama + SearXNG + audit-tools**. Это не маркетинговое описание, а рабочая модель системы.

---

## 1. Зачем RAG существует

LLM знает только то, на чём её учили. Она:

- не знает ваши файлы, внутренние инструкции банка, свежие постановления НБРБ;
- галлюцинирует статьи, даты и формулировки, если её просят «вспомнить закон»;
- не умеет честно сказать «этого нет в контексте», если контекста ей не дали.

**RAG не дообучает модель.** Он на каждый вопрос подкладывает в промпт куски ваших документов. Модель отвечает, опираясь на этот текст, а не на «память».

Правильная формулировка для аудита:

> Модель думает. Документы доказывают. RAG — механизм, который в нужный момент кладёт доказательство в окно контекста.

Без RAG чат — это энциклопедия 2023–2024 года. С RAG — это энциклопедия плюс ваша библиотека НПА на сегодня.

## 2. Что RAG делает за один запрос

Пользователь спрашивает: *«Какой срок возврата валютной выручки по аренде нерезиденту?»*

Система делает не один вызов модели, а конвейер:

```
вопрос
  → эмбеддинг вопроса (вектор)
  → поиск похожих кусков в векторной базе (+ опционально BM25)
  → отбор top-k (и rerank)
  → сборка промпта: RAG-шаблон + найденные куски + вопрос
  → LLM генерирует ответ
  → UI показывает цитаты (какой файл / какой кусок)
```

Ключевой инвариант: **модель видит только то, что попало в промпт.** Если нужная статья не попала в top-k — модель её «не знает», даже если файл лежит в Knowledge Base.

Это главное, что нужно держать в голове как разработчику. Баги RAG почти всегда не в модели, а в одном из этапов:

| Этап | Если сломан | Симптом |
|---|---|---|
| Извлечение текста | PDF/HTML распарсился в мусор | Модель «не видит» документ |
| Чанкинг | Статья разрезана пополам / слишком мелкие куски | Ответ обрывочный, путает статьи |
| Эмбеддинги | Слабая модель или другая модель, чем при индексации | Ищет «не то» |
| Retrieval | top-k слишком маленький / порог слишком высокий | Нужный абзац не попал в промпт |
| Контекст LLM | `num_ctx=2048` у Ollama | Куски подложены, но обрезаны |
| Режим вызова | Native tools, модель не вызывает search | KB прикреплена, модель игнорирует |

## 3. Два времени жизни: индексация и вопрос

RAG — это две разные фазы. Их нельзя смешивать в голове.

### 3.1 Offline: индексация (ingest)

Случается **один раз при загрузке файла** (и снова при reindex).

1. Файл попадает в систему (чат, Knowledge, API).
2. Движок извлечения достаёт текст (Tika / Docling / pypdf / HTML).
3. Текст режется на **чанки** (chunk size + overlap).
4. Каждый чанк пропускается через **embedding-модель** → вектор.
5. Вектор + текст чанка + метаданные пишутся в **vector DB**.

После этого исходный PDF можно даже не читать на каждый вопрос. Для поиска достаточно векторов и текста чанков.

### 3.2 Online: retrieval на вопрос

Случается **на каждый user message**, если к чату/модели прикреплены файлы или knowledge.

1. Вопрос эмбеддится **той же embedding-моделью**.
2. Vector DB ищет ближайшие векторы (cosine / inner product).
3. Опционально: BM25 (ключевые слова) + fusion + reranker.
4. Top-k чанков вставляются в шаблон `{{CONTEXT}}`.
5. LLM отвечает.

Эмбеддинг вопроса и эмбеддинг документов **должны быть из одной модели и одной размерности**. Сменили embedding-модель — без reindex поиск бессмысленный: векторы живут в разных пространствах.

## 4. Базовые понятия, без которых нельзя читать код

### Чанк

Кусок текста фиксированного размера (символы или токены) с перекрытием (overlap), чтобы предложение на границе не потерялось. Для законов overlap критичен: номер статьи часто в предыдущем абзаце.

Типичные значения:

- маленький контекст LLM (8k): chunk 800–1000 токенов, overlap 100, top-k 3–5;
- большой контекст (32k+), как у вас: chunk 1500–2000, overlap 150–200, top-k 10–20.

### Эмбеддинг

Функция `текст → вектор ℝⁿ`. Семантически близкие тексты дают близкие векторы.

- `all-MiniLM-L6-v2` — дефолт Open WebUI, 384 dim, слабый для русского юр. языка;
- `nomic-embed-text` — нормальный локальный baseline через Ollama;
- `qwen3-embedding` / `bge-m3` — лучше для русского и смешанных запросов.

Для НПА РБ **нельзя** оставлять MiniLM. Юридический русский + номера статей требуют multilingual / русскоязычной embedding-модели.

### Vector DB

Хранилище `(id, vector, text, metadata)`. Поиск = k ближайших соседей.

Open WebUI по умолчанию: встроенный **ChromaDB** (SQLite). Для одного инстанса этого достаточно. Для нескольких uvicorn workers SQLite не fork-safe — нужен Qdrant / pgvector / Milvus.

### Hybrid search

Семантика (векторы) плохо ловит точные идентификаторы: «ст. 625 ГК», «постановление 196», «Инструкция 38». BM25 ловит их как ключевые слова. Hybrid = dense + sparse, затем слияние (RRF / EnsembleRetriever).

Для аудита **hybrid search обязателен**.

### Reranker

После грубого top-20 отдельная модель (CrossEncoder, например `bge-reranker-v2-m3`) пересортировывает пары (вопрос, чанк) и оставляет top-k. Это второй по важности рычаг качества после embedding.

### Full context vs retrieval

- **Retrieval:** в промпт попадают только найденные куски. Масштабируется на кодексы.
- **Full context / Entire Document:** весь файл целиком. Выигрывает на коротких инструкциях (< ~20k токенов), проигрывает на ГК/НК.

Для ГК РБ full context — плохая идея. Для конкретной инструкции НБРБ на 15 страниц — часто лучше retrieval.

## 5. Как RAG устроен в Open WebUI

Open WebUI — не «магический RAG». Это FastAPI-бэкенд с явным пайплайном. Полезно знать файлы, а не только UI.

### 5.1 Карта кода

| Слой | Где | Что делает |
|---|---|---|
| UI настроек | `src/lib/components/admin/Settings/Documents.svelte` | Admin → Documents |
| Knowledge UI | `src/lib/components/workspace/Knowledge/` | коллекции документов |
| Files API | `backend/open_webui/routers/files.py` | загрузка, `process_uploaded_file` |
| Knowledge API | `backend/open_webui/routers/knowledge.py` | коллекции, `/{id}/file/add` |
| Retrieval API | `backend/open_webui/routers/retrieval.py` | конфиг RAG, `get_ef`, `get_rf`, process_file |
| Retrieval utils | `backend/open_webui/retrieval/utils.py` | loaders, embeddings, `query_collection`, hybrid |
| Vector factory | `backend/open_webui/retrieval/vector/factory.py` | `VECTOR_DB_CLIENT` |
| Chat middleware | `backend/open_webui/utils/middleware.py` | вставка контекста в запрос к LLM |
| Config | `backend/open_webui/config.py` | PersistentConfig + env |

Точка входа индексации: загрузка файла → `process_uploaded_file` → loader → splitter → embeddings → `VECTOR_DB_CLIENT.upsert`.

Точка входа вопроса: chat completion → middleware смотрит прикреплённые files/knowledge → `query_collection` / hybrid → RAG template → LLM.

### 5.2 Три способа дать модели документы

Это разные объекты. Путать их — типичная ошибка.

**A. Файл в чат (ad-hoc)**

Пользователь прикрепляет PDF/TXT в конкретный диалог. Создаётся **отдельная vector-коллекция на файл**. Живёт с чатом. Reindex Knowledge Base эти файлы **не трогает**. Сменили embedding — надо перезалить файл.

**B. Knowledge Base (коллекция)**

Workspace → Knowledge. Именованная библиотека: «НПА аренда 2026», «Политики банка», «МСА». Файлы индексируются в коллекцию с id knowledge. Можно:

- прикрепить к модели (Workspace → Models → Knowledge);
- прикрепить к чату через `#`;
- отдать модели tools (`query_knowledge_bases`), чтобы она искала сама.

Это правильное место для библиотеки НПА по проверке.

**C. Web search / `#https://...`**

Не то же самое, что Knowledge. Поиск идёт в интернет (SearXNG и др.), страницы парсятся, иногда индексируются как временный контекст. Нужен большой `num_ctx`. Для банка: только allowlist `pravo.by`, `nbrb.by` и т.д.

Ещё есть experimental **External Knowledge Sources**: Open WebUI не индексирует документы сам, а ходит в ваш Qdrant/Milvus/pgvector. Query эмбеддится моделью Open WebUI — значит embedding у внешней базы должен совпадать.

### 5.3 Два режима retrieval в чате

С версии, где Native Function Calling стал дефолтом, поведение резко меняется.

| | Legacy (function calling = default/off) | Native function calling |
|---|---|---|
| KB прикреплена к модели | Open WebUI **сам** ищет и вставляет чанки | Модель получает **tools** и должна вызвать поиск |
| KB не прикреплена | RAG нет, пока пользователь не добавит `#` | Tools могут видеть все доступные KB |
| Маленькие модели | Работает предсказуемо | Часто **не вызывают** tool → «модель не знает документы» |
| Сильные модели (70B) | Работает, но без retry поиска | Может переформулировать запрос и искать повторно |

Для аудита на сильной локальной модели native + tools — мощнее: модель может сказать «в первом поиске нет статьи, ищу иначе». Для стабильности на старте безопаснее **классический RAG** (File Context on, Builtin Tools off **или** native off), чтобы чанки всегда инжектились.

Матрица File Context × Builtin Tools:

| File Context | Builtin Tools | Поведение |
|---|---|---|
| On | Off | Классический RAG: чанки в промпте, модель не ищет сама |
| On | On | Чанки + модель может доискать tools |
| Off | On | Ничего заранее не кладут; модель читает KB/файлы tools (`query_*`, `view_file`) |
| Off | Off | Файлы игнорируются |

Отдельно: тумблер **Using Entire Document** на конкретном файле/KB обходит retrieval и пихает весь текст в каждое сообщение.

### 5.4 Шаблон RAG

Admin → Documents → RAG template. Плейсхолдер `{{CONTEXT}}` обязателен. Сюда попадают найденные чанки. Сообщение пользователя **дописывается после шаблона автоматически**.

Не ставьте `{{QUERY}}` в шаблон: вопрос тогда продублируется.

Шаблон — единственное место, где вы говорите модели, как относиться к документам. Для аудита его надо переписать, а не оставлять дефолт.

Пример логики шаблона (смысл, не копипаста UI):

```
Используй ТОЛЬКО фрагменты ниже.
Если ответа нет во фрагментах — так и скажи, не выдумывай статьи.
Цитируй: документ, статья/пункт, дословная формулировка.
Не применяй нормы РФ, ЕС, IFRS, если их нет во фрагментах.

{{CONTEXT}}
```

Env `RAG_SYSTEM_CONTEXT=True` кладёт этот контекст в **system** message, а не в user. Тогда позиция контекста не прыгает от реплики к реплике, и KV-cache / prompt cache работают. Follow-up вопросы становятся быстрее. Для длинных НПА это важно.

### 5.5 Hybrid search и rerank внутри

Если включён `ENABLE_RAG_HYBRID_SEARCH`:

1. Vector search — `VECTOR_DB_CLIENT.search`;
2. BM25 — `BM25Retriever` по текстам чанков;
3. Слияние — `EnsembleRetriever` / RRF, вес `HYBRID_BM25_WEIGHT`;
4. Rerank — `get_rf()` (CrossEncoder / ColBERT / external HTTP reranker);
5. Отсечение по `RELEVANCE_THRESHOLD`.

Практические цифры для юр. базы при большом контексте:

- Hybrid: **on**
- Top K: **20** (кандидаты до rerank)
- Top K Reranker: **8–12** (что реально уйдёт в LLM)
- Relevance threshold: начать с **0**, поднять только когда видите мусор в цитатах
- Reranker: `BAAI/bge-reranker-v2-m3` (multilingual) локально, если GPU позволяет

### 5.6 Извлечение текста

Качество RAG упирается сюда сильнее, чем в LLM.

`CONTENT_EXTRACTION_ENGINE`:

- default pypdf — ок для текстовых PDF, плох для сканов;
- **Apache Tika** — широкий набор форматов;
- **Docling** — сильнее на сложных PDF/таблицах;
- MinerU / Marker / Mistral OCR / PaddleOCR — сканы и картинки.

Для `pravo.by` HTML у вас в audit-tools уже есть свой экстрактор (BeautifulSoup → `.txt`). В Open WebUI лучше заливать **очищенный `.txt` / markdown**, а не сырой HTML с меню и футером. Мусор в чанках = мусор в ответах.

Temporary Chat парсит файлы на фронте, без бэкенд-экстракторов. Для НПА temporary chat не использовать.

### 5.7 Чанкинг в Open WebUI

- `RAG_TEXT_SPLITTER`: `character` (RecursiveCharacterTextSplitter) или `token`;
- Markdown Header Splitting: сначала режет по H1–H6, потом обычный splitter;
- `CHUNK_MIN_SIZE_TARGET`: склеивает крошечные куски (оглавление, «Статья 5.» без текста) со следующим, пока не наберётся порог, не превышая `CHUNK_SIZE`, и не смешивая файлы.

Для кодексов markdown-split + min size ~50–60% от chunk size резко уменьшает число бесполезных векторов.

Ограничение Open WebUI: сплиттер **не знает «Статья N»**. Для НПА идеальный чанкер — по статье/пункту. У вас в `audit-tools` уже есть `chunker.py` с `ARTICLE_RE`. Это лучше дефолта Open WebUI. Два рабочих пути:

1. Препроцессить текст в markdown вида `## Статья 625` и включить Markdown Header Splitting;
2. Индексировать своей нарезкой во внешний vector DB и подключить External Knowledge.

### 5.8 Где живут векторы

По умолчанию Chroma внутри volume Open WebUI. Коллекции изолированы: knowledge id, file id, memories.

Смена `VECTOR_DB` **не мигрирует** данные. Нужен reindex / повторная заливка.

Memories — отдельная фича (память о пользователе), тоже на тех же embeddings. К базе НПА отношения не имеет.

## 6. Что настраивать в Open WebUI (чеклист)

Путь в UI: **Admin → Settings → Documents** (в доках иногда «Tools → Documents»).

### Embedding

- Engine: **Ollama** (не SentenceTransformers внутри контейнера — экономите RAM WebUI и не блокируете event loop).
- Model: та же, что в audit-tools, сейчас логично `qwen3-embedding` / `bge-m3`. Не MiniLM.
- После смены модели: кнопка **Reindex**. Иначе старые векторы несовместимы.
- Chat-файлы reindex не покрывает — только Knowledge.

### Retrieval

- Hybrid search: on
- Markdown header split: on
- Text splitter: token
- Chunk size: 1500–2000 (у вас модели с большим контекстом)
- Overlap: 150–200
- Chunk min size target: ~1000
- Top K: 15–20
- Full context: off глобально, включать точечно на коротких инструкциях
- Bypass embedding: не включать (это «засунуть всё», не RAG)

### Модель чата

- Ollama **context length** в Edit model → Advanced Params: **не 2048**. Для RAG минимум 16k, лучше 32k. Иначе retrieved чанки обрежутся, и будет казаться, что RAG «не работает».
- Function calling: для стабильного «всегда подкладывай НПА» — классический RAG; для агента — native + system prompt «сначала ищи в knowledge».

### Knowledge UX

- Workspace → Knowledge → коллекция на **проверку** (не одна гигантская на все годы).
- В чате: `#` → выбрать коллекцию.
- Либо привязать коллекцию к кастомной модели «Аудитор НПА».

### Web search

Отдельный тумблер. Это не Knowledge. Для банка: SearXNG + домены allowlist. Страницы всё равно надо чистить, иначе в RAG попадёт навигация сайта.

## 7. API: как программно собрать базу знаний

Open WebUI отдаёт те же эндпоинты, что UI. Auth: `Authorization: Bearer <API key>`.

Типовой цикл (он уже начат в `audit-tools/backend/app/services/openwebui_client.py`):

```
1. POST /api/v1/knowledge/create          → knowledge_id
   GET  /api/v1/knowledge/                → найти по имени

2. POST /api/v1/files/                    → file_id
   (обработка асинхронная)

3. GET  /api/v1/files/{id}/process/status  → ждать status=completed
   НЕ вызывать file/add раньше: получите 400 "content is empty"

4. POST /api/v1/knowledge/{id}/file/add
   body: {"file_id": "..."}
```

Важные детали:

- Knowledge **не** ограничен `RAG_FILE_MAX_COUNT` (в отличие от чата). Лимит размера файла — `RAG_FILE_MAX_SIZE`.
- Заливать лучше `.txt` после вашего экстрактора, не сырой HTML.
- Если `file/add` сразу после upload — это гонка, не «пустой файл».
- Reindex knowledge: через Admin UI; chat-файлы только re-upload.

Для чата с уже готовой KB достаточно, чтобы аудитор выбрал модель с привязанной коллекцией или написал `#ИмяКоллекции`.

## 8. Как это стыкуется с вашей системой аудита

Сейчас пайплайн такой:

```
название проверки + keywords
  → LLM предлагает список НПА
  → аудитор выбирает
  → SearXNG / known_sources / manual URL
  → download в data/audit_cases/{id}/knowledge_raw/
  → .html + .txt extract
```

RAG — **следующий слой над `knowledge_raw`**, а не замена скачивания.

Правильная архитектура:

```
knowledge_raw (источник истины на диске)
    → саммари для аудитора (читать глазами)
    → чанки (+ метаданные: акт, статья, url, дата)
        → Open WebUI Knowledge  (чат «спросить закон»)
        → опционально свой индекс (если нужен контроль нарезки)
```

Клиентские Excel/выписки **не класть** в ту же KB, что НПА. Иначе модель смешает «что требует закон» и «что в файле клиента». Две коллекции:

1. `npa-{case_id}` — только нормативные тексты;
2. `case-facts-{case_id}` — если вообще нужен RAG по данным (часто лучше tools: pandas/SQL, а не RAG).

Почему: RAG по таблицам слабый. Цифры, курсы, обороты должны идти через код, не через «похожий абзац».

Ваш `chunker.py` (нарезка по «Статья/Глава») ближе к идеалу для кодексов, чем дефолт Open WebUI. Имеет смысл:

- либо нормализовать `.txt` в markdown с заголовками статей перед upload;
- либо оставить Open WebUI как UI, а retrieval делать своим сервисом.

## 9. Математика контекста (чтобы не удивляться)

Пусть chunk ≈ 1500 токенов, top-k = 12.

```
retrieved   ≈ 18 000 токенов
system+RAG  ≈ 1–2k
история чата ≈ растёт каждый ход
ответ       ≈ 1–2k
```

Нужен `num_ctx` модели заметно больше этой суммы. На 8k контексте top-k=12 с chunk 1500 физически не влезет: часть чанков выбросится, и вы будете отлаживать «не ту embedding», хотя проблема в окне.

Follow-up без `RAG_SYSTEM_CONTEXT`: каждый новый вопрос сдвигает позицию retrieved-блока → KV cache сбрасывается → ответы тормозят. Включайте system-context на длинных сессиях.

## 10. Типичные поломки и что проверять

1. **Модель не видит документ**  
   Откройте извлечённый текст. Пустой/меню сайта → чинить extractor, не LLM.

2. **Видит кусок, игнорирует нужную статью**  
   Retrieval. Включите hybrid, увеличьте top-k, проверьте, что вопрос содержит номер статьи (BM25). Сделайте чанк по границам статьи.

3. **KB прикреплена к модели, эффекта нет**  
   Native function calling: модель не вызвала tool. Либо выключите native, либо пропишите в system: сначала `query_knowledge_bases`. Проверьте File Context / Builtin Tools / глобальный Model Defaults.

4. **`NoneType.encode`**  
   Embedding-модель не загрузилась. Заново Save в Documents, проверьте Ollama `qwen3-embedding`.

5. **После смены embedding ответы стали бредом**  
   Нет reindex.

6. **400 empty content при API**  
   Не дождались `process/status=completed`.

7. **Worker умер при upload, несколько воркеров**  
   Встроенный Chroma+SQLite. Один worker или внешний VECTOR_DB.

8. **CUDA OOM**  
   Чат-70B и embedding на одном GPU. Снизить `RAG_EMBEDDING_BATCH_SIZE`, вынести embed на CPU/другой GPU, не эмбеддить во время генерации.

9. **Цитаты есть, смысл неверный**  
   В промпт попал похожий, но другой акт (ГК vs инструкция НБРБ). Лечится метаданными в чанке (`источник: постановление 196 от …`) и шаблоном «называй документ полностью». Hybrid + rerank снижают путаницу.

## 11. Чего RAG не умеет (важно для аудита)

- Не заменяет чтение первички и пересчёт. По таблицам — tools.
- Не гарантирует полноту. Top-k может пропустить соседний пункт статьи.
- Не обновляет сам себя. Скачали новую редакцию НПА — перезалейте файл (старый удалите из KB).
- Не даёт юридическую силу. Это поисковик+генератор. Аудитор подтверждает цитату по первоисточнику.
- Плохо работает, если в одном чанке смешаны несвязанные нормы — виноват чанкер.

Для банка обязателен **audit trail**: какой file_id, какой chunk, какой score ушёл в промпт. Open WebUI показывает citations в UI; для отчёта проверки лучше логировать это у себя.

## 12. Рекомендуемая схема именно под вас

Железо сильное, модели большие, задача — НПА РБ + чат аудитора.

1. **Источник:** `knowledge_raw/*.txt` после вашего download (не HTML).
2. **Нормализация:** перед заливкой разметить `## Статья N` / `## Пункт N`, заголовок документа, URL, дата.
3. **Open WebUI Knowledge:** одна коллекция на кейс проверки.
4. **Embedding:** Ollama, русскоязычная/multilingual модель, одна на ingest и query.
5. **Retrieval:** hybrid + rerank, chunk ~1500–2000, top-k 12–20.
6. **Чат-модель:** 32k+ context, RAG template «только фрагменты, цитируй, не выдумывай».
7. **Режим:** сначала классический RAG (предсказуемо). Потом native tools, когда убедитесь, что 70B стабильно вызывает search.
8. **Web search:** только для добычи новых актов в библиотеку, не как основной RAG в каждом вопросе.
9. **Данные клиента:** не в эту KB. Вопросы «сколько начислено» — через pandas/tools.
10. **API:** `openwebui_client.py` + ожидание `process/status`, иначе гонка.

Минимальный тест качества (делайте после каждой смены настроек):

- Залить одну инструкцию НБРБ, спросить точную формулировку пункта, который есть в тексте.
- Спросить номер статьи, которого **нет** — модель должна отказаться, а не сочинить.
- Спросить «ст. N» по номеру — должен сработать BM25.
- Спросить перефраз без номера — должна сработать семантика.
- Открыть citations: тот ли файл, та ли статья.

Если эти четыре теста проходят — RAG настроен. Если нет — чините этап из таблицы в §2, а не меняйте чат-модель.

## 13. Словарь

| Термин | Смысл |
|---|---|
| RAG | На вопрос подложить найденные куски документов в промпт |
| Ingest | Парсинг → чанки → векторы → запись в БД |
| Retrieval | Поиск чанков по вопросу |
| Embedding | Текст → вектор |
| Vector DB | Индекс ближайших соседей |
| Knowledge Base | Именованная коллекция в Open WebUI |
| Hybrid | Векторы + BM25 |
| Rerank | Пересортировка кандидатов кросс-энкодером |
| Top-k | Сколько чанков отдать модели |
| Full context | Отдать весь документ, без поиска |
| Reindex | Перенарезать и переэмбеддить Knowledge |
| Citation | Ссылка на чанк, из которого модель «взяла» ответ |
| Agentic RAG | Модель сама вызывает search-tools, а не получает чанки заранее |
