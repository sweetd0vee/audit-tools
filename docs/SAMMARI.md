# Как делается суммаризация

Две разные команды. Их легко перепутать.

| Команда | Откуда текст | Результат |
|---|---|---|
| `саммари` | Скачанные акты библиотеки кейса | Word: **карточка по каждому акту** + обзор проверки + приложение фрагментов |
| `саммари total` | Знания модели, **без** файлов кейса | Word: один конспект по теме |
| `гипотезы` | Саммари / total / программа / фрагменты НПА + знания модели | Excel: 8–10 гипотез для проверки |

Этот документ — про **`саммари`**: карточки существенного по базе знаний. Как пользоваться в чате: [GUIDE.md](GUIDE.md#8-история-5-саммари-в-word). Шпаргалка фраз: [AUDITOR.md](AUDITOR.md). Retrieval на `вопрос …` — другое: [RAG_для_разработчика.md](RAG_для_разработчика.md). Промпты: [PROMPTS.md](PROMPTS.md).

Инвариант:

> Модель пишет карточку существенного **для этой проверки** по отобранным фрагментам акта (query-focused RAG). Это не перечень всех статей и не аудиторское суждение. Норму в программу проверки сверяют с первоисточником.

---

## 1. Что видит аудитор

После скачивания актов в том же чате:

```
саммари
```

Синонимы: `сводка`, `бриф`, `docx`, `word`, `обзор актов`. Пересборка: `саммари заново` (также `пересобери`, `force`).

В чат полный Word не копируется — ссылка:

```
http://localhost:8100/api/v1/cases/{id}/knowledge/summary.docx
```

Плюс короткий дайджест по актам (первая строка каждой карточки).

В файле три слоя:

1. **Обзор проверки** — как акты складываются в рамку темы (нормативный контур, на что опираться, пересечения и пробелы).
2. **Карточка на каждый скачанный акт** — зачем акт в этой проверке, суть и сфера, ключевые нормы, что проверять, чего нет в выборке.
3. **Приложение** — RAG-фрагменты `[n]` со статьёй/пунктом и официальным URL. Номер `[n]` в тексте карточки — **не** статья закона, а ссылка на фрагмент в конце файла.

Повтор без `заново` отдаст уже готовый файл, если библиотека не менялась и схема карточки та же (`BRIEF_SCHEMA`, сейчас **4**).

---

## 2. Конвейер целиком

```
аудитор: «саммари»
  → Pipe (audit_agent.py) ловит фразу, не путая с «саммари total»
  → SSE  GET /api/v1/cases/{id}/knowledge/brief/stream
         (?force=true если «заново»)
  → brief_flow.build_brief_events
       1. ingest текстов из knowledge_raw → knowledge_text + case.json
       2. кэш? если Word свежий — отдать и выйти
       3. rebuild_index (нарезка всех актов на чанки)
       4. embed_index (эмбеддинги подмножество чанков по keywords)
       5. для каждого акта по очереди: summarize_item
            короткий  → oneshot_card (весь текст)
            длинный   → hybrid RAG → rag_card (stuff по [n])
       6. обзор по всем карточкам (overview)
       7. Markdown + Word + brief_sources.json в summaries/
  → Pipe пишет в чат ссылку и дайджест
```

Код: `brief_flow.py`, `knowledge_flow.py` (`summarize_item`, `retrieve_item_fragments`), `knowledge_retrieve.py`, `chunker.py`, `brief_docx.py`.

Документы идут **по одному**. Параллели нет: одна Ollama на хосте. На каждом вызове карточки модель получает **название проверки и ключевые слова**. Без них получился бы дамп «по порядку кодекса».

---

## 3. Вход из чата

Pipe, не голая модель Ollama:

1. `_is_brief` срабатывает на `саммари` / `сводка` / `бриф` / `docx` / `word` (и похожие). `саммари total` сюда **не** попадает — его ловит раньше `_is_total`.
2. Нужен `case_id` из скрытой метки `<!--audit-case:…-->` в истории чата. Нет кейса — отказ.
3. Таймаут — `max(TIMEOUT_SEC, BRIEF_TIMEOUT_SEC)`, по умолчанию **1800 с** на весь стрим.
4. Открывается SSE. Статусы из сервера (`Саммари акта 3 из 10: …`, `RAG по «ГК»: 400 чанков…`) рисуются в чате как прогресс, не как ответ модели.
5. В конце — ссылка на `summary.docx` и 4–6 строк дайджеста. Полный текст в чат не копируется.

Эндпоинты: `GET …/brief/stream`, также `POST …/brief` без стрима, скачивание `GET …/summary.docx` и `…/summary.md`.

---

## 4. Ingest: от файла к тексту

`ingest_library` обходит `knowledge_raw/` кейса:

- Берёт файлы, из которых можно извлечь текст (не дублирует HTML, если рядом уже есть `.txt`).
- Пишет очищенный текст в `knowledge_text/{stem}.txt`.
- Регистрирует `KnowledgeItem` в `case.json`: title, filename, char_count, `extract_status=ok|failed`.

Без успешных экстрактов стрим падает: «База знаний пуста. Сначала утвердите акты…».

---

## 5. Индекс и эмбеддинги

Перед карточками:

1. **`rebuild_index`** — каждый акт режется `chunk_text` (~**1600** знаков, overlap **180**). Режет по границам `Статья N` / `Глава N`, иначе по абзацам. Слишком длинную статью пилит окнами. Результат — `knowledge_index.json`: `{id, item_id, title, filename, text, embedding}`.
2. **`embed_index`** — **не** эмбеддит весь ГК. По каждому акту берёт топ-**60** чанков по пересечению с keywords проверки (+ первый чанк акта, если не попал). Батчи по 8 в Ollama `qwen3-embedding:latest`. Если Ollama недоступна — статус «эмбеддинги частично недоступны», дальше работает BM25.

На шаге карточки `select_evidence` всё равно доэмбеддит кандидатов, у которых вектора ещё нет. Предварительный `embed_index` только ускоряет.

## 6. Карточка одного акта

`summarize_item` читает полный текст из `knowledge_text/`. Порог короткий/длинный — не «число страниц», а **`sequential_windows`**: акт упаковывается в окна по ~**10 000** знаков, статьи не режутся посередине.

| Условие | Путь |
|---|---|
| Одно окно (`len(windows) ≤ 1`) | Короткий акт: весь текст в LLM |
| Два и больше окон | Длинный акт: query-focused RAG, затем один stuff-вызов |

Упавший акт не останавливает остальные: в Word попадёт пометка «карточка не собрана… читайте первоисточник».

Карточка пишется в `summaries/{файл}.md` и в `item.summary` / `item.citations` кейса.

### 6.1. Короткий акт — oneshot

Один вызов `chat_complete`:

| | |
|---|---|
| System | `docs/prompts/summary_system.txt` |
| User | `docs/prompts/oneshot_card.txt` |
| Температура | 0.1 |
| `num_ctx` | 32768 |
| `num_predict` | 8192 |
| Таймаут | 420 с |

В user: название проверки, keywords, title акта, **оглавление** (до 80 заголовков «Статья/Глава…» — ориентир, не обязанность выписать всё), **полный текст**.

Задача модели — не конспект всех статей, а карточка существенного под эту проверку.

Цитаты в приложение: равномерная выборка окон по акту (`fragments_from_item`, до 24), не RAG.

### 6.2. Длинный акт — retrieve → stuff

Паттерн production RAG: **retrieve → MMR → stuff**. Без map-reduce по главам, без RAPTOR/GraphRAG.

#### Запросы (без лишнего LLM)

`retrieval_queries(state, extra=[название акта])`:

- название проверки;
- все keywords одной строкой;
- каждый keyword по отдельности (до 8);
- topics (до 4);
- title акта.

Несколько коротких запросов лучше одного длинного: BM25 ловит «аренда» и «валюта» порознь.

#### Hybrid retrieval (`select_evidence`)

По **этому** акту (не по всей библиотеке):

1. Каждый запрос даёт два ранжирования: **Okapi BM25** и **keyword overlap** (счёт вхождений + Jaccard токенов).
2. Списки сливаются **RRF** (Reciprocal Rank Fusion, k=60) — без общей шкалы «BM25 vs cosine».
3. Берётся пул кандидатов (~**80**). Первый чанк акта всегда в пуле (`always_include_first`): преамбула/сфера часто нужна карточке.
4. Эмбеддятся запросы и кандидаты без вектора. Dense-ранги (cosine к `qwen3-embedding`) снова сливаются через RRF.
5. Если в запросе есть «ст. N» — чанк с заголовком «Статья N» получает большой boost, чтобы не выиграть перекрёстная ссылка.
6. **MMR** (λ=**0.7**): из пула оставляют **16** чанков — релевантность минус похожесть на уже взятые. Иначе 16 почти одинаковых абзацев про аренду.
7. Соседи ±1 чанк, **но не чужая статья**: «Статья 626» не приклеивается к хиту «Статья 625». Продолжение той же статьи без нового заголовка — можно.
8. Подряд идущие хиты сливаются в один span, пока не кончится бюджет **~14 000** знаков. Модель видит целые статьи, не обрубки.

Если RAG вернул пусто — запас: топ-8 чанков по `keyword_score`.

Эмбеддинги, посчитанные на этом шаге, дописываются в `knowledge_index.json`.

#### Один LLM-вызов `rag_card`

Тот же `summary_system`, user — `docs/prompts/rag_card.txt`:

- проверка и keywords;
- размер акта в знаках (честно: это не весь текст);
- оглавление **всего** акта (до 80 заголовков) — чтобы модель знала, чего в выборке нет;
- отобранные фрагменты `[n] Заголовок статьи\nтекст`.

Правила промпта: норму брать только из фрагментов; каждую ключевую норму подкрепить `[n]`; не выписывать статью, которая есть только в оглавлении.

Если модель вернула текст без `## Ключевые нормы` и без `## Основные положения`, сервер дописывает заголовок `## Ключевые нормы`, чтобы обзор и Word не развалились.

## 7. Что должно получиться в карточке

Одинаковая схема для короткого и длинного акта (`BRIEF_SCHEMA = 4`):

| Раздел | Зачем |
|---|---|
| **Зачем этот акт** | 2–4 предложения: роль именно в этой проверке |
| **Суть и сфера** | На кого распространяется, что регулирует, с какой даты — только если сказано в тексте |
| **Ключевые нормы** | Обычно 5–15 пунктов: `- ст./п. N — норма и зачем аудитору` (+ `[n]` на длинном акте) |
| **Что проверять** | 5–10 объектов / документов / расчётов из норм |
| **Чего нет в тексте** | Честный пробел: чего важного для проверки нет во фрагментах / в акте |

Объём, который просят у модели: примерно страница (2200–4500 знаков). Плотность важнее полноты. Нельзя: нормы РФ/ЕС/IFRS, суждение «нарушение», выдуманные ставки и даты.

---

## 8. Обзор проверки

Когда карточки всех актов готовы (или помечены как failed):

1. Карточки склеиваются (обрезка суммарно до **20 000** знаков).
2. Один вызов: `summary_system` + `docs/prompts/overview.txt`.
3. Модель пишет три блока: нормативный контур, на что опираться в первую очередь, пересечения и пробелы. Не копировать карточки дословно. 1500–2500 знаков.
4. Если LLM упала или вернула пусто — детерминированный запас `_synthesize`: список актов и первые 12 буллетов из «Ключевые нормы» / «Что проверять» каждой карточки. Обзор без модели всё равно будет, просто суше.

## 9. Сборка Word

Пишутся три файла в `data/audit_cases/{id}/summaries/`:

| Файл | Содержание |
|---|---|
| `sammari_{проверка}_{case}.docx` | То, что скачивает аудитор |
| `brief.md` | Тот же текст markdown |
| `brief_sources.json` | Фрагменты приложения |

`write_brief_docx`: титул, обзор, карточки по актам, приложение. Ссылки `[n]` в тексте — кликабельные якоря на фрагмент. У фрагмента: статья/пункт, excerpt, официальный URL скачивания (из `found_url` документа кейса).

Приложение берёт `item.citations` (то, что отобрал RAG / oneshot). Если цитат нет — равномерная выборка по акту, до 24 фрагментов на документ.

Мета в `case.json`: путь к docx, число актов, `schema=4`.

---

## 10. Кэш

`artifact_stale`: Word считается свежим, если файл на диске есть, `schema` совпадает и число успешно извлечённых актов то же. Тогда стрим сразу отдаёт ссылку, модель не зовут.

`саммари заново` → `?force=true` → кэш игнорируется, карточки и Word пересобираются.

Сменили промпт карточки так, что нужна другая схема — поднимите `BRIEF_SCHEMA`, иначе аудиторы будут получать старый Word.

## 11. Сколько вызовов модели и сколько ждать

| Шаг | Вызовов LLM | Ещё |
|---|---|---|
| Короткий акт | 1 | — |
| Длинный акт | 1 | эмбеддинги чанков (не LLM) |
| Обзор проверки | 1 на всю библиотеку | запас без LLM, если упало |

Пример: 8 инструкций + ГК → ≈ **9** вызовов `qwen3.8:27b`, не десятки окон map-reduce. Часто несколько минут, не 15–40.

| Где | Секунды | На что |
|---|---|---|
| `summary_timeout_sec` | 420 | Один вызов карточки или обзора |
| `brief_timeout_sec` / Valve `BRIEF_TIMEOUT_SEC` | 1800 | Весь стрим `саммари` |

|---|---|---|

## 13. Куда карточки уходят дальше

Саммари — не тупик. Готовые карточки подмешиваются:

| Куда | Как |
|---|---|
| `вопрос …` | Блок «конспекты актов» — **ориентир**, какой это документ. Номер статьи модель должна брать из дословных фрагментов, не из карточки |
| `программа проверки` | Карточки как ориентир по нормам, если саммари уже собрано |
| `гипотезы` | Карточки + total + программа + фрагменты НПА |

Поэтому «не ту статью» в `вопрос` лечится retrieval вопроса, а не переписыванием карточки. Карточка намеренно неполная: это выжимка под тему проверки.

---

## 14. Чем саммари не является

| Это не | Потому что |
|---|---|
| `вопрос …` | Вопрос ищет чанки под конкретный вопрос по всей библиотеке; саммари — карточка **одного** акта под тему проверки |
| `саммари total` | Total **не открывает** файлы кейса; один вызов из знаний модели |
| Полный конспект кодекса | Плотность важнее полноты; RAG берёт топ по теме |
| Аудиторское суждение | Промпт запрещает «нарушение / не нарушение» |
| Цитата для рабочей документации | Норму сверяют с первоисточником / `вопрос …` |

---

## 15. `саммари total` (сосед, не этот конвейер)

Команда `саммари total` / `конспект модели`. `total_flow.py`: один вызов `total_system` + `total_user`, без ingest и без RAG. Модель пишет конспект «из головы» с разделом «Источники» `[n]` (номера она помнит, URL часто «неизвестен»). Файл в `totals/`. Это черновик ориентира, не норма из библиотеки.

## 16. Карта для разработчика

```
audit_agent.py              _is_brief → SSE brief/stream
brief_flow.py               ingest → index/embed → summarize_item × N → overview → docx
knowledge_flow.py           oneshot | retrieve_item_fragments + rag_card
knowledge_retrieve.py       BM25 + dense → RRF → MMR → merge (не склеивать чужие статьи)
chunker.py                  chunk_text по «Статья N», bm25_scores, rrf_fuse, mmr_select
brief_docx.py               Word, якоря [n], гиперссылки на URL акта
prompts/summary_system.txt  роль на все вызовы карточки и обзора
prompts/oneshot_card.txt    короткий акт
prompts/rag_card.txt        stuff по [n]
prompts/overview.txt        обзор в начале Word
```

Тесты: `backend/tests/test_brief.py` — `TestSummarizeFullDocument` (длинный акт не уходит в map-reduce), `TestRetrieveEvidence` (BM25+MMR предпочитают статьи по теме).
