# Как работает саммари

Две разные команды. Их легко перепутать.

| Команда | Откуда текст | Результат |
|---|---|---|
| `саммари` | Скачанные акты библиотеки кейса | Word: карточка **по каждому акту** + обзор проверки |
| `саммари total` | Знания модели, **без** файлов кейса | Word: один конспект по теме |

Этот документ — про **`саммари`**: карточки по базе знаний. Как пользоваться в чате: [GUIDE.md](GUIDE.md#8-история-5-саммари-в-word). Шпаргалка фраз: [AUDITOR.md](AUDITOR.md). Retrieval на `вопрос …` — другое: [RAG_для_разработчика.md](RAG_для_разработчика.md).

Инвариант:

> Модель пишет карточку существенного **для этой проверки** по отобранным фрагментам акта (query-focused RAG). Это не перечень всех статей и не аудиторское суждение. Норму в программу проверки сверяют с первоисточником.

---

## 1. Что видит аудитор

После скачивания актов в том же чате:

```
саммари
```

Синонимы: `сводка`, `бриф`, `docx`, `word`. Пересборка: `саммари заново`.

В чат полный Word не копируется — ссылка:

```
http://localhost:8100/api/v1/cases/{id}/knowledge/summary.docx
```

В файле три слоя:

1. **Обзор проверки** — как акты складываются в рамку темы.
2. **Карточка на каждый скачанный акт** — зачем акт в этой проверке, ключевые нормы, что проверять, чего нет в выборке.
3. **Приложение** — RAG-фрагменты `[n]` со статьёй/пунктом и официальным URL.

Повтор без `заново` отдаст уже готовый файл, если библиотека не менялась и схема карточки та же.

---

## 2. Конвейер целиком

Pipe ловит фразу `саммари` и открывает SSE:

`GET /api/v1/cases/{id}/knowledge/brief/stream`

(при `заново` — `?force=true`).

```
библиотека кейса
  → ingest текстов
  → rebuild_index + эмбеддинги по keywords
  → для каждого скачанного акта: карточка существенного
       короткий акт  → один вызов LLM (весь текст)
       длинный акт   → query-focused RAG → один stuff-вызов
  → один вызов: обзор по карточкам
  → Word + Markdown в summaries/
```

Код: `brief_flow.py`, `knowledge_flow.py`, `knowledge_retrieve.py`.

На каждом вызове карточки модель получает **название проверки и ключевые слова**. Без них получился бы дамп «по порядку кодекса».

Документы идут **по одному**. Параллели нет: одна Ollama на хосте.

## 3. Карточка одного акта

Текст акта берётся из `knowledge_text/`. Дальше:

### Короткий акт (одно окно ~≤10 000 знаков)

Один вызов `oneshot_card` по полному тексту.

### Длинный акт — query-focused RAG (не map-reduce)

Паттерн из production RAG: **retrieve → MMR → stuff** (LangChain stuff + hybrid search; без RAPTOR/GraphRAG — слишком дорого для локальной Ollama).

1. Акт режется на чанки (`chunk_text`, ~1400 знаков по статьям).
2. Несколько запросов: название проверки, keywords по отдельности и вместе.
3. **Hybrid retrieval:** BM25 + keyword overlap + dense embeddings (Ollama).
4. Списки рангов сливаются через **RRF** (Reciprocal Rank Fusion).
5. **MMR** (λ≈0.7) убирает почти одинаковые куски и оставляет разные статьи.
6. Соседи ±1 чанк + склейка подряд идущих — чтобы статья не разрезалась.
7. Один LLM-вызов `rag_card` по отобранным фрагментам `[n]`.

Бюджет контекста — `summary_max_chars` (~14 000). Обычно **1 вызов модели на акт**, а не десятки map+reduce.

Карточка сохраняется в `summaries/{файл}.md` и в `case.json`. Упавший акт не останавливает остальные.

---

## 4. Сколько вызовов модели

| Шаг | Вызовов |
|---|---|
| Короткий акт | 1 |
| Длинный акт | 1 (+ эмбеддинги чанков, без LLM) |
| Обзор проверки | 1 на всю библиотеку |

Пример. 8 инструкций и ГК РБ → ≈9 LLM-вызовов вместо десятков окон map-reduce. На `qwen3.8:27b` библиотека часто укладывается в **несколько минут**, а не 15–40.

### Таймауты

| Где | Секунды | На что |
|---|---|---|
| `summary_timeout_sec` | 420 | Один вызов карточки |
| `brief_timeout_sec` / Valve `BRIEF_TIMEOUT_SEC` | 1800 | Весь стрим `саммари` |

### Кэш Word

Готовый Word отдаётся сразу, если файл есть, число актов то же, схема карточки та же (`BRIEF_SCHEMA`, сейчас **4**). `саммари заново` пересобирает всё.

---

## 5. Чем саммари не является

| Это не | Потому что |
|---|---|
| `вопрос …` | Вопрос ищет чанки под конкретный вопрос; саммари — карточка по теме проверки |
| `саммари total` | Total не открывает файлы кейса |
| Полный конспект кодекса | Плотность важнее полноты; RAG берёт топ по теме |

Карточки потом подмешиваются в `вопрос …` и в программу проверки.

---

## 6. Параметры

| Параметр | Сейчас | Смысл |
|---|---|---|
| `summary_rag_top_k` | 16 | Сколько чанков после MMR |
| `summary_rag_candidates` | 80 | Пул кандидатов до MMR |
| `summary_rag_neighbor` | 1 | Соседи слева/справа |
| `summary_rag_mmr_lambda` | 0.7 | Релевантность vs разнообразие |
| `summary_max_chars` | 14000 | Бюджет текста в `rag_card` |
| `summary_section_chars` | 10000 | Порог «короткий акт» (oneshot) |
| `summary_timeout_sec` | 420 | Таймаут одного LLM-вызова |

```

brief_flow.py           ingest → index/embed → summarize_item × N → overview → docx
knowledge_flow.py       oneshot | retrieve_item_fragments + rag_card
knowledge_retrieve.py   BM25 + dense → RRF → MMR → merge
chunker.py              bm25_scores, rrf_fuse, mmr_select
prompts/rag_card.txt    stuff по [n]
```
