# Как работает саммари

Две разные команды. Их легко перепутать.

| Команда | Откуда текст | Результат |
|---|---|---|
| `саммари` | Скачанные акты библиотеки кейса | Word: карточка **по каждому акту** + обзор проверки |
| `саммари total` | Знания модели, **без** файлов кейса | Word: один конспект по теме |

Этот документ — про **`саммари`**: карточки по базе знаний. Как пользоваться в чате: [GUIDE.md](GUIDE.md#8-история-5-саммари-в-word). Шпаргалка фраз: [AUDITOR.md](AUDITOR.md). Retrieval на `вопрос …` — другое: [RAG_для_разработчика.md](RAG_для_разработчика.md).

Инвариант:

> Модель читает акт и пишет карточку существенного **для этой проверки**. Это не перечень всех статей и не аудиторское суждение. Норму в программу проверки сверяют с первоисточником.

---

## 1. Что видит аудитор

После скачивания актов в том же чате:

```
саммари
```

Синонимы: `сводка`, `бриф`, `docx`, `word`. Пересборка: `саммари заново`.

В чат полный Word не копируется — ссылка:

```
http://localhost:8100/api/v1/cases/{id}/knowledge/summary.docx
```

В файле три слоя:

1. **Обзор проверки** — как акты складываются в рамку темы (нормативный контур, на что опираться, пересечения и пробелы).
2. **Карточка на каждый скачанный акт** — зачем акт в этой проверке, суть и сфера, ключевые нормы, что проверять, чего нет в тексте.
3. **Приложение** — фрагменты `[n]` со статьёй/пунктом и официальным URL. Номер `[n]` — ссылка на фрагмент в конце файла, не номер статьи закона.

Повтор без `заново` отдаст уже готовый файл, если библиотека не менялась и схема карточки та же.

---

## 2. Конвейер целиком

Pipe ловит фразу `саммари` и открывает SSE:

`GET /api/v1/cases/{id}/knowledge/brief/stream`

(при `заново` — `?force=true`).

```
библиотека кейса
  → ingest текстов
  → для каждого скачанного акта: карточка существенного
       короткий акт  → один вызов LLM
       длинный акт   → окна по тексту → заметки → одна карточка (map-reduce)
  → один вызов: обзор по карточкам
  → Word + Markdown в summaries/
```

Код: `backend/app/services/brief_flow.py` (сборка Word), `knowledge_flow.py` (карточка акта).

На каждом вызове карточки модель получает **название проверки и ключевые слова**. Без них получился бы дамп статей «по порядку кодекса». С ними — только то, что меняет работу аудитора по этой теме.

Документы идут **строго по одному**, окна внутри акта — тоже по одному. Параллели нет: одна Ollama на хосте, длинный контекст, так надёжнее, чем гонять десять кодексов сразу.

---

## 3. Карточка одного акта

Текст акта берётся целиком из `knowledge_text/` (очищенный HTML/PDF). Это **не RAG**: ключевые слова не отбирают чанки и не выкидывают середину кодекса.

Дальше акт режется на **последовательные окна** (`sequential_windows`):

- статьи/главы пакуются, пока окно не превысит ~10 000 знаков (`summary_section_chars`);
- граница статьи не режется пополам;
- overlap (~300 знаков) только если одна статья длиннее окна.

### Короткий акт (одно окно)

Один вызов. Модель сразу пишет карточку:

- **Зачем этот акт** — роль в этой проверке;
- **Суть и сфера**;
- **Ключевые нормы** — обычно 5–15 пунктов, не все статьи подряд;
- **Что проверять**;
- **Чего нет в тексте**.

Объём карточки — примерно страница (2200–4500 знаков).

### Длинный акт (несколько окон)

Map-reduce:

1. **Map.** По каждому окну модель выписывает только существенное для проверки (`ст./п. N — суть и зачем аудитору`). Если в окне нечего брать по теме — одна строка «нет существенного». Пустой ответ переспрашивается один раз.
2. **Reduce.** Все заметки (до 24 000 знаков) складываются в **одну** карточку той же структуры. Части не склеиваются как есть.

Статусы в чате вроде «читаю акт 3 из 10», «часть 4 из 12 — существенное для проверки» — это этот цикл, не зависание.

Карточка сохраняется в `summaries/{файл}.md` и в `case.json` (`item.summary`). Упавший акт не останавливает остальные: в Word будет пометка «карточка не собрана», первоисточник остаётся в библиотеке.

## 4. Много документов

«Много» здесь — и **много актов в библиотеке**, и **несколько толстых кодексов**. Поведение разное.

### Сколько вызовов модели

Пусть в кейсе *N* скачанных актов, из них *L* длинных.

| Шаг | Вызовов |
|---|---|
| Короткий акт | 1 |
| Длинный акт | число окон (+ редко retry) + 1 reduce |
| Обзор проверки | 1 на всю библиотеку |

Пример. 8 инструкций по ~15 страниц и ГК РБ:

- 8 коротких → 8 вызовов;
- ГК на десятки окон → десятки map + 1 reduce;
- обзор → 1.

Итого не «один саммари», а **линейно по актам и по длине каждого акта**. На `qwen3.8:27b` один вызов — десятки секунд или минута. Восемь коротких актов — минуты. Библиотека с кодексом — часто **15–40 минут**. Это нормально.

### Таймауты

| Где | Секунды | На что |
|---|---|---|
| `summary_timeout_sec` | 420 | Один вызов Ollama на окно / карточку |
| `brief_timeout_sec` / Valve `BRIEF_TIMEOUT_SEC` | 1800 | Весь стрим `саммари` в Pipe |

Если в кейсе несколько кодексов, 30 минут Pipe могут кончиться раньше, чем reduce последнего акта. Тогда в чате ошибка таймаута, часть карточек уже лежит в `summaries/`. Имеет смысл увеличить `BRIEF_TIMEOUT_SEC` в Valves Pipe и повторить `саммари заново`.

### Кэш Word — не кэш карточек при пересборке

Готовый Word отдаётся сразу, если:

- файл на диске есть;
- число успешно извлечённых актов не изменилось;
- схема карточки та же (`BRIEF_SCHEMA`, сейчас 3).

Иначе весь конвейер идёт заново. **Добавили один акт — перечитываются все**, не только новый. `саммари заново` всегда перечитывает все. Промежуточные `.md` карточек при этом перезаписываются.

Это главное ограничение на большой библиотеке: стоимость растёт как «все акты × длина», даже если изменился один файл.

### Где объём обрезается, даже если акты прочитаны

Карточка по акту строится по полному тексту. Дальше появляются потолки:

| Место | Лимит | Что будет на большой библиотеке |
|---|---|---|
| Reduce | в промпт уходит не больше 24 000 знаков заметок | у очень длинного акта хвост заметок может не попасть в финальную карточку |
| Обзор проверки | карточки обрезаются до 20 000 знаков суммарно | при 8–12 карточках обзор видит не все акты целиком, в первую очередь начало списка |
| Дайджест в чате | первые 6 актов | остальные только в Word |
| Приложение `[n]` | до 24 фрагментов на акт, равномерная выборка по тексту | не каждая статья кодекса в конце Word |

Обзор — рамка проверки, не оглавление всех карточек. Полные карточки всё равно идут в Word **каждая**, даже если обзор их «не дочитал».

### Практично на большой библиотеке

1. Сначала утвердите **обязательные** акты, напишите `саммари`, читайте карточки. Дополнительные акты — вторым заходом (`саммари заново` после докачки).
2. Не кладите в один кейс «все НПА банка». Keywords в названии проверки должны быть узкими: от них зависит, что модель сочтёт существенным.
3. Кодексы (ГК, НК, БК) — самые дорогие. Инструкция на 20 страниц дешёвая.
4. Если саммари сорвалось по таймауту — не обязательно начинать проверку с нуля: часть карточек уже в `summaries/`, повтор допишет Word (но перечитает акты заново).
5. `саммари total` **не замена** большой библиотеке. Это конспект «из головы» модели, без файлов. Для нормы из скачанного акта — `саммари` или `вопрос …`.

## 5. Один очень большой документ

ГК / НК / инструкция на сотни статей:

- модель **читает акт от начала до конца** окнами, ничего не пропускает в середине;
- в карточку попадает не дамп, а существенное для keywords;
- если заметок больше 24 000 знаков, reduce видит усечённый набор — приоритет у того, что успело войти (порядок окон = порядок текста, режется хвост);
- приложение Word не цитирует все статьи: 24 точки по длине акта (начало, середина, конец).

Карточка кодекса на проверку «аренда, валюта, НДС» должна быть про аренду, расчёты, валюту — не про все 1000+ статей ГК. Если в карточке «статья 1, 2, 3 … подряд» — это регресс алгоритма, не «так задумано».

---

## 6. Чем саммари не является

| Это не | Потому что |
|---|---|
| RAG / `вопрос …` | Саммари читает акт целиком. Вопрос ищет чанки по сходству |
| `саммари total` | Total не открывает файлы кейса |
| Программа проверки | Программа — процедуры СВА. Карточки актов ей только ориентир |
| Суждение «нарушение / не нарушение» | Промпт это запрещает |
| Полный конспект кодекса | Плотность важнее полноты |

Карточки потом подмешиваются в `вопрос …` (до ~18 000 знаков, приоритет актам, которые ближе к формулировке вопроса) и в программу проверки, если саммари уже собрано.

## 7. Файлы, схема, API

```
data/audit_cases/{case_id}/
  summaries/
    brief.md
    sammari_{проверка}.docx
    brief_sources.json
    {имя_акта}.md          ← карточка одного акта
  case.json                ← item.summary, meta.brief.schema
```

| API | Зачем |
|---|---|
| `GET …/knowledge/brief/stream` | Прогресс + сборка |
| `POST …/knowledge/brief` | То же без стрима |
| `GET …/knowledge/summary.docx` | Скачать Word |
| `GET …/knowledge/summary.md` | Markdown |

Схема карточки (`BRIEF_SCHEMA`) сейчас **3**. Смена схемы делает Word «устаревшим»: следующий `саммари` пересоберёт файл, даже если число актов то же.

Параметры в `backend/app/config.py`:

| Параметр | Сейчас | Смысл |
|---|---|---|
| `summary_section_chars` | 10000 | Размер окна длинного акта |
| `summary_section_overlap` | 300 | Только если статья длиннее окна |
| `summary_timeout_sec` | 420 | Таймаут одного вызова карточки |
| `brief_timeout_sec` | 1800 | Весь brief на сервере |
| `ollama_num_ctx` | 32768 | Окно модели; окно акта ~10k должно влезать вместе с промптом |
| температура карточек | 0.1 | Меньше вольности в формулировках |

## 8. Короткая карта для разработчика

```
audit_agent.py          _is_brief → SSE brief/stream
brief_flow.py           ingest → summarize_item × N → overview → docx
knowledge_flow.py       sequential_windows → oneshot | map+reduce
chunker.py              окна по статьям, even_sample для приложения
brief_docx.py           Word
```

Тесты алгоритма: `backend/tests/test_brief.py` (`TestSummarizeFullDocument` — one-shot видит keywords, длинный акт идёт окнами и reduce).
