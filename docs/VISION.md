# Продукт: коробочный Audit Copilot

Не «ещё один чат с LLM» и не конструктор для разработчика.  
**Коробка**, которую аудитор банка РБ ставит один раз и работает: как Cursor для кода, только для внутренней проверки.

Cursor победил не тем, что написал IDE с нуля. Он взял VS Code и сделал из него законченный продукт: мнение, дефолты, качество ответа, ощущение «просто работает». Мы делаем то же самое со стеком **Open WebUI + Ollama + SearXNG + тонкий Audit Tool Server**.

---

## Кому и зачем

Внутренний аудитор банка каждый раз заново собирает НПА, читает кодексы, проектирует тесты, пишет working papers. Модель без документов галлюцинирует статьи. Документы без модели не масштабируются.

Инвариант (не ломаем):

> Модель не заменяет чтение первоисточника и не ставит аудиторское суждение. Она ускоряет поиск нормы, черновик теста и черновик WP. Цитата проверяется по файлу в кейсе.

Клиентские данные и формулировки проверки **не уходят в интернет**.

Как аудитор работает в чате сегодня: [GUIDE.md](GUIDE.md).

## Качество «как Cursor»

Это не метафора про UI. Это планка продукта.

| Cursor | Мы |
|---|---|
| Поставил — открыл — пишешь код | Поставил — открыл — ведёшь проверку |
| VS Code не форкали, обвязали | Open WebUI не форкаем, обвязываем |
| Мнение из коробки: модели, shortcuts, агент | Мнение из коробки: RAG-шаблон, allowlist, фазы проверки, tools |
| Цитата из *этого* репозитория, не «вообще из интернета» | Цитата из *этого* утверждённого акта, не «вообще из памяти модели» |
| Один вход: окно редактора | Один вход: чат Open WebUI (плюс файлы кейса на диске) |
| Не заставляет собирать стек руками | `compose up` / инсталлятор, не «поднимите 6 сервисов по вики» |

Если аудитор должен прочитать README, выбрать embedding, включить hybrid search и привязать Knowledge — это не продукт, это стенд разработчика.

## Принцип сборки

**Минимум своего кода. Максимум готовых инструментов.**

Пишем только то, чего нет на рынке:

1. жизненный цикл **кейса проверки** (система записи);
2. домен РБ: allowlist, known sources, нарезка НПА по статьям, разделение «норма ≠ факт»;
3. tools, которые агент вызывает (propose / select / download / тест / WP / rule);
4. audit trail.

Не пишем:

- чат, citations, auth, загрузку файлов, Knowledge UI;
- свой LLM-рантайм;
- свой поисковик;
- свой редактор WP, если хватает шаблона `.docx` + генерации;
- второй фронт «потому что Open WebUI недостаточно красивый».

Свой React в `frontend/` — **лаборатория API**, не витрина продукта. Решение: не вкладываться, пока чат + tools не закроют поток. Если закроют — удалить.

## Один контур, один вход

Аудитор живёт в **одном окне**. Не в трёх: Vite + Swagger + Open WebUI.

```
Аудитор открывает http://audit.local
        │
        ▼
   Open WebUI  (единственная поверхность)
        │  tools / pipeline / knowledge
        ▼
   Audit Tool Server  (система записи, домен)
        │
        ├─ Ollama
        ├─ SearXNG (только добыча актов)
        └─ файлы кейса на диске
```

Чат — поверхность. Ядро — кейс: какие акты утверждены, какие файлы скачаны, какие тесты и WP появятся дальше.

## Граница продукта

| Делаем | Не делаем |
|---|---|
| Коробка: compose/инсталлятор, мнение, дефолты | SaaS с клиентскими файлами во внешней LLM |
| Сборка стека + тонкий доменный сервер | Форк Open WebUI, своя модель, свой чат «с нуля» |
| Библиотека НПА, RAG с цитатами, черновики тестов и WP | Юридически значимое заключение «за аудитора» |
| Allowlist доменов РБ | Поиск по всему интернету |
| Human-in-the-loop на список НПА, тесты, выводы | Автоподпись working paper |
